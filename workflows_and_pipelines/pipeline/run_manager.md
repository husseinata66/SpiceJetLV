# 1. Component Name

**Run Manager**

# 2. Purpose

The Run Manager is an orchestration component responsible for preparing, organizing, monitoring, and finalizing every execution run of the Agentic AI Testing Platform pipeline.

**It is not an AI Agent.** It never analyzes software behavior, never forms an opinion about whether observed behavior is correct, never generates Findings, and never generates test cases. It has no judgment role anywhere in the pipeline. Its entire responsibility is mechanical: give every run a unique identity, a well-organized workspace, and a running record of what happened — nothing about *whether* what happened was good or bad.

Where the eight Agents (Project Context, Explorer, Test Design, Manual Execution, Automation, Automation Execution, Self-Healing, Reporting) answer "what does the application do, and what should be tested, manually validated, built, run, and reported," the Run Manager only answers "which run is this, where does its output go, and what state is it in."

# 3. Non-Responsibilities

To keep this component's boundary unambiguous, the Run Manager explicitly must **not**:

- Analyze, interpret, or judge application behavior.
- Generate, classify, score, or triage Findings (that is the Explorer Skill's responsibility — see `.claude/skills/explorer-skill/SKILL.md`).
- Generate, design, or modify test cases (Test Design Skill) or automation scripts (Automation Skill).
- Decide whether a run "passed" or "succeeded" in a quality sense — it records mechanical status (§8), not a verdict.
- Modify the content of any artifact an Agent produces.
- Substitute for, or bypass, any Human Review / Automation Approval checkpoint defined in `workflows_and_pipelines/pipeline/pipeline.md` §5.
- **Create, activate, or write to a module.** `platform_core_data/modules/` — including `modules.json` and every module's `module.json` — belongs to the **Module Manager** (`module_architecture.md` §6.6). The Run Manager *reads* the active-module pointer when creating a run, to record `modules[]`/`moduleScope` (§7); it never sets it. Two writers for one pointer is how a pointer stops being trustworthy.

**Note on the run folder name, Title, and Description (§5, §7):** generating these is mechanical *selection/formatting* of context that already exists elsewhere (the Run Scope, a User Story/Bug ID, a Feature/Module name) via a deterministic function (§5.5) — never an analytical judgment about the application under test, and never an AI-generated summary. It does not cross into Findings, test-case generation, or quality verdicts, and it does not weaken the boundary in this section.

# 4. Responsibilities

The Run Manager must:

1. **Generate a self-descriptive run folder name** for every execution run, per the naming convention in §5 — always by calling `platform_core/tools/run_manager` (§5.5), never hand-formatted.
2. **Generate a Run Title and Description** (§7) — a short human-readable title and a longer descriptive summary of the run's objective, generated from the same Scope/Target context as the folder name.
3. **Validate filesystem-safe naming** — the naming utility itself sanitizes every segment (§5.5); the Run Manager must not bypass it and hand-format a folder name directly.
4. **Prevent duplicate folder names** — confirm the resulting Run Workspace folder name does not already exist before creating it; the utility appends a deterministic numeric suffix on collision (§5.5).
5. **Create the Run Workspace** — the directory structure in §6 — before any Agent begins work for that run.
6. **Generate Run Metadata** (`run.json`, §7) at the start of the run and keep it current as the run progresses.
6a. **Maintain the Active Run pointer** (`current_active_run.json`, §5.7), the per-run code-state anchor (`targetRef`, §5.8), and run lineage (`lineage.json`, §5.9) — the Run Manager is the only writer of all three.
6b. **Record the run's module scope** — `modules[]`, `moduleScope`, and `moduleArtifactRefs[]` in `run.json` (§7), read from the Module Manager's active-module pointer at creation. It records that scope; it never decides or changes it.
7. **Provide workspace paths to downstream agents** — the concrete, run-scoped paths each Agent should treat as its working directory for that run's artifacts.
8. **Track execution status** — maintaining the run's current state from the Execution Status enum (§8) as the run moves through the pipeline.
9. **Maintain artifact organization** — ensuring every artifact produced during the run lands in the correct subdirectory of the Run Workspace (§6), without altering the content of any artifact.
10. **Publish a Run Summary** (`run_summary.md`, §9) once the run reaches a terminal status.

# 5. Run Naming Convention

**Revision note (2026-07-23, index prefix added 2026-07-27):** this revision replaces the `RUN-YYYYMMDD-XXX[-slug]` folder-naming scheme (§5.1/§5.2 in every prior revision of this document) with a self-descriptive convention that encodes the run's index, Scope, and Target directly in the folder name, so a run can be identified without opening it. Folder names are generated by calling the reusable module at `platform_core/tools/run_manager/` (§5.5) — never hand-formatted by an agent and never an AI-generated slug (the previous Display Name concept is retired; it was never actually produced by any real run — see §5.6). No existing run folder is renamed by this revision itself; see §5.6 for how legacy folders are handled.

## 5.1 Folder Name Format

```
[<owner>-]run-NNN__YYYY-MM-DD_HH-mm-ss__[Scope]__[Module-or-UserStory]
```

- `<owner>` — the Feature or module the run belongs to (§5.1.1). Absent on an unowned run.
- `run-NNN` — the run's **1-based run index within its owner's sequence**, zero-padded to 3 digits (`run-001`, `run-042`). The index is derived mechanically as **one past the highest index that owner already has in the runs directory** — `reissue-run-003` is the third Reissue run, whatever other Features did in between. Unowned `run-NNN` folders form one more sequence of their own. Legacy and otherwise unindexed folders (created before this convention) are ignored when computing it rather than guessed at. An index past three digits keeps its full width rather than being truncated (`run-1000`). The prefix is generated by the naming utility (§5.5), never hand-formatted.
- `YYYY-MM-DD_HH-mm-ss` — the run's start time, keeping the timestamp ahead of the descriptive segments so folders still sort chronologically as plain strings within a single owner's sequence.
- `[Scope]` — one of the canonical Run Scopes (§5.2), never left as free text.
- `[Module-or-UserStory]` — the module, feature, or User Story/Bug ID the run targets (e.g. `FlightSearch`, `US-245_AddCabinClassFilter`), sanitized to a filesystem-safe form.

Examples:

```
run-001__2026-07-23_10-35-18__FullRun__FlightSearch
run-002__2026-07-23_11-02-41__Smoke__Login
run-003__2026-07-23_14-20-05__Regression__BookingFlow
run-004__2026-07-23_15-48-55__Targeted__US-245_AddCabinClassFilter
run-005__2026-07-23_16-10-32__Targeted__AgencyManagement
reissue-run-003__2026-10-04_17-23-43__UserStory__ReissueFlowManualExecution
ancillaries-run-002__2026-09-26_20-51-48__Targeted__Ancillaries-FlynasNDCSeatMap
agency+branch-run-001__2026-09-23_22-36-43__UserStory__AutoReissueCheckbox-AgencyandBranch
```

## 5.1.1 Run Owner — per-Feature and per-module numbering

**Revision note (2026-10-08):** runs used to share one global `run-NNN` counter. Parallel branches (`reissue`, `ancillaries-airindia-run007`, `SeatMap`) each minted their own `run-006`, `run-007`, … and the numbers collided the moment those branches met. Each Feature and module now numbers its own runs, and the folder name says whose run it is.

The owner is **derived from the scope fields `run.json` records** (§7), never from the target text or a folder name:

| The run records | Owner | Example prefix |
|---|---|---|
| `scopeFamily: "supplier-feature"`, `feature: F` | the Feature | `reissue-run-003` |
| `modules: [m]` | the module | `agency-run-004` |
| `modules: [a, b, …]` | the modules, sorted, joined with `+` | `agency+branch-run-001` |
| `modules: [m]`, `moduleFeature: F` (classic Feature) | `<module>.<feature>` | `agency.bulk-export-run-001` |
| `moduleScope: "full-project"`, or nothing | none | `run-006` |

The **Supplier is not part of the owner**: runs are numbered per Feature, and the Supplier already shows in the target segment and in `run.json`. A refinement run (§5.9) joins the sequence of the run it refines.

Pass the scope when the run is created, so the tooling can name it: `cli.js new --feature <F> (--supplier <S> | --shared-scope <SS>)` for a Supplier Feature run, `cli.js new --modules <m>[,<m2>] [--module-feature <F>]` for a module or classic Feature run. The default naming verb accepts the same flags.

**Moving existing runs onto their owner's sequence** is the one sanctioned exception to "a run folder is never renamed" (§5.6), and it needs explicit human approval:

```bash
node platform_core/tools/run_manager/cli.js rename-runs [--assign "<run>=<owner>,…"]          # plan, writes nothing
node platform_core/tools/run_manager/cli.js rename-runs … --apply --approved-by "<name>" --reason "…"
```

The plan lists every rename, every run left alone, and every error, and nothing is applied while an error remains. A run whose `run.json` records no scope (classic runs created before `modules[]` existed) is **left as it is** unless a human assigns its owner with `--assign` — an owner is never guessed. Each owner's renamed runs are numbered after the highest index it already holds, in start-time order. Applying a plan (`renameRuns.js`):

1. renames the folder, keeping its timestamp, scope, target, and any `__N` suffix verbatim;
2. rewrites every reference to the old name in the data root's text files in one pass (Run Manifests, lineage, registry `lastRun` paths, report links) — `--no-rewrite-refs` skips this; binary files such as `.xlsx` are never edited;
3. records the new `folderName`/`index`/`runOwner` in `run.json`, plus a `renamedFrom` history entry with the approver and reason;
4. moves the Active Run pointer (§5.7) if it pointed at a renamed run;
5. adds `{ legacyName, renamedTo }` to `.run_folder_index.json`, so the **old name keeps resolving** through `resolveRunFolder()`.

## 5.2 Canonical Run Scopes

Every folder name's Scope segment is exactly one of:

`FullRun` · `Regression` · `Smoke` · `Sanity` · `Targeted` · `Module` · `UserStory`

A run that only executed specific tests must read as `Targeted` (or another narrower scope) — it must never be named in a way that reads as a full/complete execution when it wasn't. Free-text scope/run-type input is normalized onto this set (e.g. `"Full Regression"` → `Regression`, `"Entire Project"` → `FullRun`, `"Custom"`/`"Bug"` → `Targeted`, `"Feature"` → `Module`, `"User Story"` → `UserStory`); anything unrecognized but non-empty also resolves to `Targeted` rather than silently defaulting to `FullRun`. Missing scope information resolves to `Unknown`.

## 5.3 Target Segment

The Module-or-UserStory segment is selected in this priority order: User Story ID/title → Module name → Feature name → free-text scope description. Missing/empty input resolves to `Unknown` rather than an empty segment.

## 5.4 Uniqueness, Duplicate Prevention, and Sanitization

1. Every segment is sanitized before the folder name is assembled: filesystem-unsafe characters are stripped, whitespace is collapsed, leading/trailing separators are trimmed, and the result is capped at 60 characters. An empty result after sanitization becomes `Unknown`.
2. Before creating the Run Workspace (§6), the Run Manager confirms the resulting folder name does not already exist under the project's runs directory. On collision, a deterministic `__2`, `__3`, … suffix is appended — never a randomized or silently overwritten name.
3. Because the folder name itself is index-ordered, time-ordered, and content-derived, no separate immutable Run ID is required for new runs; `run.json`'s own `folderName` field (§7) is the stable reference, and its `index` and `runOwner` fields (§7) restate the folder name's `<owner>-run-NNN` prefix. The prefix itself is produced by the naming module's `formatRunIndex()`/`nextRunIndex()` helpers (§5.5), never assembled by hand. Index order is meaningful only within one owner; `cli.js list` orders runs by start time.

## 5.5 The Naming Utility (single source of truth)

All of the above is implemented once, as code, at `platform_core/tools/run_manager/`:

- `runFolderName.js` — `generateRunFolderName(metadata, { existingNames, now, index, withIndex })` is the function every agent/skill/script must call to obtain a new run's folder name. By default it prefixes the name with `[<owner>-]run-NNN__` (§5.1), taking the index one past the highest that `metadata.owner` already has in `existingNames`; passing an explicit `index` pins it, and passing `{ withIndex: false }` omits the prefix entirely (used only by legacy migration, §5.6). It also exports `deriveRunOwner(runJson)` (the owner rule of §5.1.1), `formatRunIndex(index, owner)` (formats the prefix segment), `nextRunIndex(existingNames, owner)` (computes the owner's next index, ignoring unindexed/legacy folders), `parseRunFolderName()` (recognizes this convention with or without the prefix — returning `index` and `owner` when present — and the legacy `RUN-YYYYMMDD-XXX[-slug]` form), `normalizeScope()`, and `sanitizeSegment()`.
- `cli.js` — a thin CLI wrapper (`node platform_core/tools/run_manager/cli.js --scope <Scope> --target <Target> --started <ISO time>`) for agents/humans that aren't calling the module directly from JS. It also accepts the owner flags of §5.1.1, `--index <N>` to pin the run index explicitly, and `--no-index` to omit the prefix.
- `renameRuns.js` — `planRunRenames()`/`applyRunRenames()` move existing runs onto their owner's sequence (§5.1.1), plan-then-apply, behind `cli.js rename-runs`.
- `runFolderIndex.js` / `migrate.js` — the Legacy Run Folder Compatibility layer (§5.6).
- `activeRun.js` — the Active Run pointer (§5.7): `resolveActiveRunFolder()` is what a stage calls to resolve `{{RUN_FOLDER}}`, and `setActiveRun()` is the only writer of `platform_core_data/runs/current_active_run.json`.
- `targetRef.js` — the Target Project code-state anchor (§5.8): `captureTargetRef()` at run creation, `computeDrift()` to report what moved since. Read-only against the target, and a staleness marker only — never a source of requirements (§5.8 scope boundary).
- `runLineage.js` — run refinement (§5.9): `planRefinement()`/`writeLineage()` create a new run that inherits and supersedes an earlier one, and `resolvePriorRunFolder()` is the first actual resolver for `{{PRIOR_RUN_FOLDER}}`.
- `createRun.js` — the single run-creation path (§5.10): `createRun()` always attempts the code-state anchor, always writes `metadata/` + `RunManifest.md`, and activates only when asked. `backfillTargetRef()` anchors a run that never had one, flagged as backfilled.
- `runManifest.js` — the Run Manifest writer (§5.11): `renderRunManifest()`, `recordStage()`, `recordReuse()`, `recordGap()`, `readManifest()`. Append-only, with validated checkpoint/Invocation-Path vocabularies.

No agent, skill, or script may hand-format a run folder name inline — doing so is exactly the duplicated-string-formatting problem this module exists to eliminate. See `platform_core/tools/run_manager/__tests__/` for the behavioral test suite covering sanitization, scope normalization, collision handling, and parsing.

## 5.6 Legacy Run Folder Compatibility Index

Every run folder that existed before this revision keeps its original `RUN-YYYYMMDD-XXX[-slug]` name and content **exactly as-is** — none are renamed by this revision. This is not a blanket policy exception; it is the outcome of a real, general safety check (`runFolderIndex.js`'s `isRenameSafe()`), which physically renames a legacy folder (via `git mv`, never copy+delete) only when zero other files in the project reference that folder's name. Applying that check to every run folder that exists as of this revision found real, live references (cross-run path dependencies where one run's automation package was extended in place by a later run, generated code paths, and manifest/history-table citations) — so every one of them stays on its legacy name, and is represented instead in a per-project compatibility index:

```
platform_core_data/runs/.run_folder_index.json   (or platform_core_data/runs/.run_folder_index.json)
```

Each entry records `{ legacyName, inferredNewName, confidence, source }` — `source` names exactly which document the Scope/Target were inferred from (`metadata/run.json`, that project's `run_configuration.md` history table, or its `*_RunManifest.md`), and `confidence` is `low` whenever no metadata could be found at all (in which case `inferredNewName` uses `Unknown` segments rather than a guess). `runFolderIndex.js`'s `resolveRunFolder(runsDir, identifier)` looks up either a legacy Run ID/folder name or a new-convention name and returns the real on-disk folder — this is what keeps history lookups, dashboards, and manifests working under either naming style without rewriting any of them.

Running the migration (`node platform_core/tools/run_manager/migrate.js --project <Name>`) is non-destructive (dry-run by default; writes only the index file), idempotent (re-running produces an unchanged index for folders already indexed), and reversible (an `--apply`-driven rename, on the rare folder that passes the safety check, is a plain `git mv` and trivially reverted). Backward compatibility takes priority over forcing a rename — a folder never gets renamed just because it would be convenient. The one sanctioned exception is moving runs onto their owner's sequence (§5.1.1), which needs a named approver and keeps every old name resolvable through this same index.

## 5.7 Active Run Pointer — which run is the pipeline working on?

**Added 2026-07-27 (user-mandated).** §5.1–§5.6 answer *what a run is called*. This section answers a
separate question that nothing previously owned: **of the many runs under `platform_core_data/runs/`,
which one is the pipeline currently writing to?**

A project accumulates runs. Before this revision every stage resolved `{{RUN_FOLDER}}` from
conversational context, so "continue the Leave run" and "start a new run" were indistinguishable to
the tooling — and Stage `5A` output could land in a run whose Stage 3 belonged to something else. The
pointer makes the current run an explicit, inspectable fact on disk:

```
platform_core_data/runs/current_active_run.json
```

### The pointer is sticky

`setActiveRun()` rewrites the pointer, and **every subsequent stage targets that run until it is
switched again.** Switching to an older run is therefore a normal, first-class operation: point at it,
then invoke whichever stage needs to run or re-run. There is no per-command run argument to forget.

### It is a pointer, never a second copy of run state

The run's own `metadata/run.json` (§7) stays authoritative for status, scope, and target. Fields
duplicated into the pointer (`status`, `title`, `startedTime`) are a **display cache**, refreshed on
every `use` and by `refresh`. Where the two disagree, `run.json` wins — the pointer is a bookmark,
not a source of truth, and no stage may branch on its cached copy of a value `run.json` also carries.

### Schema

| JSON key | Description |
|---|---|
| `schemaVersion` | Pointer format version (currently `1`). A reader that encounters a **higher** version fails loudly rather than misreading an older shape |
| `activeRun.folderName` | The run folder this pipeline is currently working in — the value `{{RUN_FOLDER}}` resolves to |
| `activeRun.index` | The run's 1-based ordinal from its `run-NNN` prefix (§5.1); `null` for legacy/unindexed runs (§5.6) |
| `activeRun.scope` / `activeRun.target` | Parsed from the folder name, falling back to `run.json`; `null` when neither carries them |
| `activeRun.status` | Cached from the run's `run.json` `status` (§8 enum) — display only |
| `activeRun.title` / `activeRun.startedTime` | Cached from `run.json` — display only |
| `activeRun.stagesPresent` | Which stage folders actually exist for this run, in pipeline order — how "where did this run get to?" is answered without trusting a possibly-stale status field (§6) |
| `activeRun.path` | The run folder's repo-relative path, for direct use in messages and artifact headers |
| `switchedAt` | ISO timestamp the pointer was last changed |
| `setBy` | Who/what switched it — a human's identifier if known, else `"Run Manager"` |
| `previousRun` | The folder name this pointer replaced, so a mis-switch is one command to undo. `null` on the first switch. Re-setting the already-active run **carries the prior value forward** rather than recording the run as its own predecessor |
| `note` | Optional free-text reason for the switch; omitted entirely when absent |

### Rules

1. **A stage never invents a run folder.** It resolves `{{RUN_FOLDER}}` via `resolveActiveRunFolder()`
   (or `cli.js active`). When that returns `null`, the stage **asks which run to use** — it does not
   guess, and it does not create a new run as a fallback. Guessing is what scatters one logical run's
   artifacts across several folders.
2. **A pointer naming a folder that no longer exists is an error, not a prompt to fall back.**
   `isActiveRunStale()` reports it and `cli.js active` exits non-zero, so a deleted/renamed run
   surfaces immediately instead of silently redirecting writes into an unrelated run.
3. **Only the Run Manager writes this file.** Stages read it. A stage that needs a different run asks
   for the switch; it does not edit the pointer to redirect its own output mid-stage.
4. **Creating a run and activating it are distinct steps.** `generateRunFolderName()` (§5.5) produces a
   name; `setActiveRun()` points at a folder that already exists. `setActiveRun()` **refuses a
   nonexistent folder**, so a typo fails at the switch rather than at some later stage's write.
5. **Legacy runs are switchable by bare Run ID.** The pointer resolves identifiers through
   `resolveRunFolder()` (§5.6), so `use RUN-20260706-001` works without anyone typing the full
   legacy folder name, and legacy folders are still never renamed.
6. **The pointer is committed, not ignored.** Which run a project is working on is shared state a
   teammate or a later session needs; git history of this file is also a usable audit trail of when
   attention moved between runs.

### Tooling

Implemented at `platform_core/tools/run_manager/activeRun.js`, exported through the module barrel, and
covered by `__tests__/activeRun.test.js`:

- `resolveActiveRunFolder(runsDir)` — **the accessor a stage uses to resolve `{{RUN_FOLDER}}`.** Returns
  `null` rather than guessing when there is no pointer or the pointed-at folder is gone.
- `setActiveRun(runsDir, identifier, { now, setBy, note })` — switch. Requires an explicit `now`
  (never defaulted internally, matching `generateRunFolderName`'s contract) so callers stay
  deterministic and testable.
- `readActiveRun` / `isActiveRunStale` / `clearActiveRun` / `refreshActiveRun` / `listRuns`.

CLI verbs (the naming form in §5.5 is unchanged and still the default, so existing callers are
unaffected):

```bash
node platform_core/tools/run_manager/cli.js list                # every run, newest first, active marked *
node platform_core/tools/run_manager/cli.js use <run-or-RunID>  # switch (sticky)
node platform_core/tools/run_manager/cli.js active              # bare folder name -> {{RUN_FOLDER}}
node platform_core/tools/run_manager/cli.js active --json       # the whole pointer
node platform_core/tools/run_manager/cli.js refresh             # re-cache status/stages
node platform_core/tools/run_manager/cli.js clear               # remove the pointer
```


## 5.8 Target Project Code-State Anchor (`targetRef`)

**Added 2026-07-27 (user-mandated).** A run's artifacts describe the application *as it was when the
run executed*. Revisit that run months later and its Findings may describe code that no longer
exists. Before this revision `run.json` carried 26 fields and **not one anchored the application's
code state** — every `*Version` field is a *platform spec* version — so "is this run still current?"
could only be asked of a human (`workflows_and_pipelines/workflows/user_story_run.md` Step 1 does
exactly that). This section makes it computable.

### Fields added to `run.json` (§7)

| JSON key | Description |
|---|---|
| `targetRef` | The Target Project's **path-scoped** git commit at run creation — the code state this run's conclusions are about. `null` when the target has no resolvable git repository, which is recorded, never guessed around |
| `targetRefScope` | The repo-relative paths `targetRef` was scoped to (the in-scope surface). Empty means repo-wide — coarser, still usable |
| `targetRefCapturedAt` | ISO timestamp the anchor was taken |
| `targetRepoRoot` | The resolved target repository root, so a later reader can tell *which* repo the ref belongs to |
| `targetRefReason` | Why the ref is what it is — including why it is `null`. An unversioned target is not an unchanged one, and the distinction is stated rather than implied |

Path-scoping matters for the same reason the automation baseline's Baseline Ref is path-scoped
(§12.3 of `pipeline.md`): in a monorepo an unrelated commit elsewhere must never look like a change
to the code under test.

### The drift report

`computeDrift()` compares a run's recorded anchor against the target's current state and returns
exactly one status. **Every "unknown" is its own answer** — collapsing any of them into "unchanged"
is how a stale run's findings get silently trusted:

| Status | Meaning |
|---|---|
| `unchanged` | No commits touched the scoped paths since this run was created |
| `moved` | Commits landed; the report names the count and every changed file |
| `unknown-no-git` | The Target Project has no resolvable git repository — drift is not computable |
| `unknown-no-anchor` | This run recorded no `targetRef` (created before anchoring existed, or git was unavailable) |
| `unknown-unresolvable` | The recorded ref is not in the target's current history (rewritten, shallow clone, different repo) |

### Scope boundary — this is not requirements-from-code

`pipeline.md` §6 Rule 9 / §13 forbid the Target Project's **commit history as a source of intent**:
requirements, business rules, acceptance criteria, and expected behaviour never come from code or
history. This anchor does not do that and must never be extended to. It reads commit identity **only
as a staleness marker** — the same category as reading source to understand a selector or a route,
which that section explicitly permits as "a technical fact". It answers *"did these paths change?"*,
never *"what should the expected behaviour be?"*.

It is strictly **read-only** against the Target Project (`git log`, `git rev-list`,
`git diff --name-only`). It never stages, commits, or writes anything there; `pipeline.md` §13.3's
prohibition is unaffected. Because the automation lifecycle's `discoverRepo` deliberately asserts
every path lies inside the repository governing `platform_core_data/`, the target's repository is
reached through its own separate, write-incapable handle in `platform_core/tools/run_manager/targetRef.js`.

## 5.9 Run Lineage — refining an earlier run (`inherit + supersede`)

**Added 2026-07-27 (user-mandated). Narrowed 2026-07-29.** A user builds their automation project
across many runs. Later they want to **enhance something an earlier run delivered** — but the result
must apply to the project's **current** state, not the state when that run executed.

> **Narrowing note (2026-07-29):** this mechanism previously carried *design* artifacts forward
> between runs, which is what made "which copy of the Project Context is current?" a question needing
> machinery to answer. The Module Workspace now does that natively — a module's design is durable and
> the next run simply reads its current state (`module_architecture.md` §9.2). **Lineage remains for
> what it was always actually for: relating one *execution* to another** — a re-run of the same scope
> after a fix, a regression pass superseding an earlier one's conclusions. `inheritedArtifacts[]` now
> lists execution artifacts only. Everything else below is unchanged, and
> `{{PRIOR_RUN_FOLDER}}`/`resolvePriorRunFolder()` still resolve exactly as before.

### Refinement creates a new run; it never edits the old one

Refining `run-002` creates a **new** run that:

1. records `inheritsFrom: run-002` and `supersedes: run-002`,
2. **references** run-002's approved artifacts by path rather than copying them wholesale
   (`pipeline.md` §7 "Cross-run reuse"),
3. anchors itself to the target's **current** code state (§5.8), so its scope is today's project,
4. carries the **drift report** for run-002 → now, so stages know which inherited conclusions are
   suspect instead of assuming all of them still hold.

**run-002 is never written to.** Editing it in place would break the documented
"`runs/` — per-run, immutable once written" contract *and* destroy the record of what that run
actually concluded, which is the only evidence its Final QA Report was ever true. run-002 stays valid
*as of its own `targetRef`*; the new run is what is true now. (spec-kit calls this convention
"flow-forward" and contrasts it with amend-in-place; the immutability argument is why this platform
takes the same side.)

### `metadata/lineage.json`

| JSON key | Description |
|---|---|
| `inheritsFrom` | The prior run this refinement derives from — **the resolver `{{PRIOR_RUN_FOLDER}}` never had** |
| `supersedes` | The run whose conclusions this one replaces, for the scope they share |
| `priorRunPath` | Repo-relative path to the prior run, for direct use in artifact headers |
| `inheritedArtifacts[]` | Per stage: `{stage, approved, path, files}` — referenced, not copied. **Narrowed 2026-07-29 to *execution* artifacts** (`manual_execution/`, `execution/`, `reporting/`): design artifacts are resolved from the module registry at their current revision and need no inheritance. `approved` is read from each artifact's own `status:` field (§7 of `pipeline.md`); a Pending artifact is **listed, not hidden**, because inheriting one is a legitimate declared choice |
| `drift` | The §5.8 drift report for prior-run → now, frozen at refinement time |
| `recordedAt`, `setBy`, `reason` | Provenance of the refinement decision |

`{{PRIOR_RUN_FOLDER}}` now resolves: `resolvePriorRunFolder(runsDir, folderName)`. It appears in
`pipeline.md` §7, `user_story_run.md`, and `README.md`, and until this revision **nothing resolved
it** — it was a placeholder a human filled in. `lineageChain()` walks the full ancestry
newest-first and is cycle-guarded, since a hand-edited `lineage.json` could otherwise loop.

### Rules

1. **A refinement never mutates the run it inherits from.** Not its artifacts, not its `run.json`,
   not its status. The only write is into the *new* run.
2. **Inherited artifacts are referenced, not copied** (`pipeline.md` §7). A stage that needs to
   *evolve* one copies it into the new run once, at that point, and records the origin.

   **(a) Design artifacts are never inherited at all.** A refinement reads
   `modules/{module}/{stage}/` at its current revision and records that revision in
   `moduleArtifactRefs[]` (§7). Copying a module artifact into a run would recreate the
   "which copy is current?" problem this narrowing removed.
3. **A refinement is anchored to today**, never to the prior run's `targetRef` — that is the whole
   point: the enhancement applies to the project's current state.
4. **Drift is reported, never silently tolerated.** A `moved` or any `unknown-*` status means
   inherited findings covering the changed paths need re-verification before reuse. A stage must not
   present an inherited conclusion as current when drift says otherwise.
5. **`supersedes` is a claim about conclusions, not a deletion.** The prior run remains readable,
   valid for its own anchor, and part of the audit trail.

### Tooling

`platform_core/tools/run_manager/runLineage.js` (plan/apply split, mirroring the automation
lifecycle's merge plan): `planRefinement()` computes and returns without writing;
`writeLineage()` records it into an already-created run folder; `readLineage()`,
`resolvePriorRunFolder()`, `lineageChain()`, `inspectInheritable()` read.

```bash
node platform_core/tools/run_manager/cli.js refine <prior-run> --dry-run   # inspect the plan
node platform_core/tools/run_manager/cli.js refine <prior-run> --reason "..." --scope-paths src/leave
node platform_core/tools/run_manager/cli.js drift [--run <r>] [--json]     # exit 2 when not unchanged
```

`refine` creates the run folder, writes `run.json` (with today's anchor) and `lineage.json`, then
makes the new run active. `--dry-run` shows the plan — including what would be inherited and the
drift — and creates nothing.


## 5.10 Run Creation (single code path)

**Added 2026-07-27 (user-mandated).** §5.1–§5.6 name a run; §5.7–§5.9 track, anchor, and relate runs.
This section covers **bringing one into existence**, which until now was a *prose checklist* repeated in
each workflow's Step 1.

That mattered because the code-state anchor (§5.8) was written only if someone followed the spec line
saying to. `cli.js refine` was the only path that actually wrote one, with inline logic nothing else
could reuse — so a run created any other way silently lost the ability to answer "has the application
moved since?", the very question §5.8 exists to make answerable.

`platform_core/tools/run_manager/createRun.js` makes the invariants **structural rather than
remembered**:

| Invariant | Why it cannot be skipped |
|---|---|
| **The anchor is always attempted** | `captureTargetRef()` runs on every creation. Where there is no target root or no git, `targetRef` is `null` **with `targetRefReason` stating why** — an unversioned target is not an unchanged one (§5.8), and that distinction only survives if the reason is recorded at creation, not inferred later |
| **`metadata/` and `RunManifest.md` always exist** | §6 makes `metadata/` the one folder every run has, and §5.11's Manifest is the orchestrator's own source of truth. A run without one was invisible to "where are we right now?" |
| **A missing anchor is declared as a gap** | The Manifest's Declared Gaps section records it, so drift reading `unknown-no-anchor` later is explained rather than mysterious |
| **Stage folders are NOT created** | A run only has folders for stages it reached (§6). Pre-creating them was the behaviour the 2026-07-17 revision removed, and creating a run must not reintroduce it |
| **Activation is separate and explicit** | `activate: true` writes the pointer. Creation and switching stay distinct (§5.7 Rule 3, §5.9), so creating a run for later never silently steals focus from the one in progress |
| **An existing folder is never overwritten** | A run folder is immutable once written (§6); `createRun` refuses rather than merging into it |

```bash
node platform_core/tools/run_manager/cli.js new --scope <Scope> --target <Target> \
  [--workflow first_run] [--scope-paths src/leave,src/shared] [--no-activate] \
  [--feature F (--supplier S | --shared-scope SS) | --modules m[,m2] [--module-feature F]]
```

The owner flags (§5.1.1) put the run in its Feature's or module's own sequence; without them it is an
unowned `run-NNN`.

`cli.js refine` (§5.9) now routes through the same creator, so a refinement run gets identical
guarantees rather than a parallel implementation.

### Backfilling an anchor

A run created before §5.8 — or while git was unavailable — carries no `targetRef`, so drift reads
`unknown-no-anchor` forever. `backfillTargetRef()` (`cli.js anchor`) anchors it to *now* and records
`targetRefBackfilled: true` plus a reason stating that **the anchor is the code state at backfill time,
not at execution time**. That caveat is mandatory: drift measured from a backfilled anchor *understates*
what actually changed since the run, and without the flag a reader would mistake it for evidence the run
was verified against that commit. Backfill refuses to overwrite a real anchor unless explicitly forced.

## 5.11 Run Manifest Writer

**Added 2026-07-27 (user-mandated).** `pipeline.md` §7 has always required a Run Manifest at
`runs/{{RUN_FOLDER}}/metadata/RunManifest.md` recording, per stage: timestamp, checkpoint status,
approving reviewer, revision count, Invocation Path, and a link to the artifact. **Nothing wrote it.**
`migrate.js` only ever *read* legacy `*_RunManifest.md` files for metadata inference, and the sole
creation instruction was prose in each workflow's Step 1 — so the pipeline's own source of truth for run
state was maintained by hand, if at all.

`platform_core/tools/run_manager/runManifest.js` writes it. The rendered shape is authoritative in
[`platform_core/templates/metadata/RunManifest.md`](../../platform_core/templates/metadata/RunManifest.md);
the module is its renderer, and where the two disagree the template is the spec.

### Append-only, like the artifacts it tracks

- A **stage row** is added, or updated in place for a stage already present — one row per stage.
- **Checkpoint History is only ever appended to.** A `Rejected` entry keeps its feedback, because the
  revision that followed is what the reviewer asked for and losing the reason makes that revision
  unreviewable.
- **Re-recording an unchanged status appends nothing.** Bookkeeping is not a decision, and padding
  history with it buries the real transitions.
- Nothing rewrites history. (This mirrors spec-kit's `/converge`, whose only write is an appended
  section and which leaves its file byte-identical when there is nothing to add.)

### Validated vocabularies

`recordStage()` rejects any checkpoint status outside `pipeline.md` §7's four
(`Pending Review` / `Pending Automation Approval` / `Approved` / `Rejected`) and any Invocation Path
outside §5.3.1 #7's three (`Pipeline` / `Direct` / `Direct (degraded)`). A typo fails loudly instead of
entering the orchestrator's source of truth as an unrecognized state.

### Cross-run reuse gets a writer, not just a slot

`recordReuse()` writes the Cross-Run Reuse row `pipeline.md` §7 requires — source run, `Referenced`
vs `Copied`, whether it was approved there, and the drift since. **When drift is anything but
`unchanged`, a Drift Implication note is added stating that inherited conclusions covering changed paths
are unverified against current code** (§5.9 Rule 4) — stated once per manifest, not repeated per row.
`cli.js refine` calls this for every inherited artifact, so the §7 obligation is discharged
mechanically.

```bash
node platform_core/tools/run_manager/cli.js stage "Stage 1 — Project Context" \
  --status Approved --reviewer <name> --revisions 2 --invocation Pipeline
node platform_core/tools/run_manager/cli.js manifest            # the stage ledger, as data
node platform_core/tools/run_manager/cli.js manifest --gap "..." --why "..."
node platform_core/tools/run_manager/cli.js manifest --reuse <artifact> --from <run>
```

`readManifest()` returns the ledger as structured data, so an orchestrator can answer "where are we
right now?" without parsing prose — the question §7 says this artifact exists to answer.


# 6. Workspace Structure

**Revision note (2026-07-25 single-project restructure · 2026-07-27 `workspace/` removal · 2026-07-29 module split):** the project is fully self-contained under `platform_core_data/`, with no project-name path segment. Two earlier shapes are now superseded. The 2026-07-25 revision described a current-approved tree under `platform_core_data/workspace/` alongside run folders — removed on 2026-07-27, when the Run Folder became the sole artifact location. **The 2026-07-29 revision narrows the Run Folder to execution artifacts only**: design output (Stages 1, 2, 3, 4A, 5H) now lives in a durable **Module Workspace** under `platform_core_data/modules/{module}/`, specified in [`module_architecture.md`](module_architecture.md) and summarized by `pipeline.md` §7's two-location table. This section also consolidates the previously cross-cutting `evidence/`, `screenshots/`, `videos/`, `logs/`, `network/` folders into the owning stage's own folder rather than keeping them as separate top-level run folders — no evidence type is dropped, only regrouped by which stage produces it.

**The Run Folder holds execution and run bookkeeping. Nothing else.**

**On-demand folder creation:** the Run Manager creates only `metadata/` before any Agent starts — every run has one, regardless of which stages it reaches. Every other subfolder is created **only at the moment the corresponding Agent actually produces its first output**, never upfront as an empty placeholder:

```
platform_core_data/
  runs/
    {{RUN_FOLDER}}/          <- e.g. run-001__2026-07-23_10-35-18__FullRun__FlightSearch (§5)
      metadata/              <- always created immediately
        RunManifest.md         where the run is right now (§5.11)
        run.json               status, scope, target (§7)
        SafetyPreflight.md     the run's mutation footprint, written by 4M/5A BEFORE executing
        SafetyAuthorizations.json / .md
                               run-scoped human approvals — see the note below
        observability/         run telemetry (`pipeline.md` §15) — created on first event
          ObservabilityEvents.jsonl    append-only evidence, one event per line
          ObservabilityMetrics.json    derived, regenerable — never hand-edited
          ObservabilityReport.md       human-readable
          ObservabilityDashboard.html  self-contained, offline, presentation only
                             ---- MANUAL branch ----
      manual_execution/      <- created only when Stage 4M writes to it
                             ---- AUTOMATION branch ----
      execution/             <- created only when Stage 5A writes to it
      reporting/             <- created only when Stage 6A writes to it
```

**`context/`, `discovery/`, `test_design/`, `automation/`, and `self_healing/` are no longer created in a run folder.** A run reads those artifacts from the module workspace and records which revision of each it consumed (§7's `moduleArtifactRefs[]`). A pre-existing run that already holds them keeps them exactly as they are — backward compatibility outranks layout consistency, the same rule §5.6 applies to legacy folder names.

**Naming note:** every reference to a run's workspace path elsewhere in this document uses the placeholder `{{RUN_FOLDER}}` for brevity. For a run created under this document's current naming convention, that placeholder resolves to the full `run-NNN__YYYY-MM-DD_HH-mm-ss__Scope__Target` folder name (§5); for a pre-existing run, it resolves to that run's original `RUN-YYYYMMDD-XXX[-slug]` folder name, which is never renamed (§5.6).

A run that executes nothing — created, then abandoned before Stage 4M or 5A — has exactly `metadata/` on disk. That is a complete and accurate record: the run existed and executed nothing.

**Execution Safety artifacts live in `metadata/`, and that placement is load-bearing** (added 2026-08-07, `pipeline.md` §14). A run-scoped authorization sits *inside the run folder it belongs to*, so one run structurally cannot read another's — cross-run leakage is prevented by layout, not only by a rule someone has to remember. Each record additionally carries its own `runId`, re-checked on load, so even a copied file authorizes nothing.

**Observability telemetry lives in `metadata/observability/`, for the same structural reason** (added 2026-08-07, `pipeline.md` §15). It gets a subfolder rather than four more flat files because the four artifacts are always produced and consumed together, and `metadata/` should stay the place where run state lives rather than the place where everything lands. The isolation guarantee is identical to the Safety one and defended the same way twice: placement inside the run folder, plus a `runId` on every event that is re-checked on load, so a copied stream contributes nothing to another run's metrics.

Only `ObservabilityEvents.jsonl` is evidence. The other three are **derived and regenerable at any time** from it, which is why none of them is ever hand-edited — an edited metric is a metric with no evidence behind it. A run created before 2026-08-07 has no `observability/` folder at all and reports **Not Instrumented**; no event is fabricated to fill the gap.

Both files are written by the executing stage (`4M` / `5A`), never by the Run Manager, and both are run evidence under §7's immutability rules once written. **A run approval never becomes project policy** — nothing in `metadata/` is ever promoted into `knowledge_base/execution_safety_policy.json`.

**Which folders exist records which branch the run took** (`pipeline.md` §3.3, §6 Rule 3a). The two pipelines share Stages 1–3 (whose output is per module) and then diverge:

| Run took | Folders present | Folders never created |
|---|---|---|
| **Manual branch only** | `metadata/`, `manual_execution/` | `execution/`, `reporting/` |
| **Automation branch only** | `metadata/`, `execution/`, `reporting/` | `manual_execution/` |
| **Both branches** | all of the above | — |

**A branch not taken is not a gap.** An absent `execution/` folder means the run delivered the Manual pipeline in full — not that stages were skipped (`pipeline.md` §6 Rule 3a).

- `metadata/` — `run.json` (§7), `run_summary.md` (§9), `lineage.json` (§5.9), and the Run Manifest (`RunManifest.md`, `pipeline.md` §7 — the per-stage record of timestamp, checkpoint status, approving reviewer, revision count, Invocation Path, and the module artifacts consumed), plus any other run-bookkeeping file. The one folder every run has, always.
- `manual_execution/` — **Manual branch (Stage 4M), terminal.** Manual Execution Results, Manual Execution Summary, **Manual Test Results CSV**, **Manual QA Report** (this branch self-reports — it has no downstream Reporting stage), and captured evidence (screenshots, videos, notes, logs) for this run. **Never contains a script of any kind** (`manual-execution-skill` §2.1). A multi-module run writes **one** consolidated result set here, with every result citing its module.
- `execution/` — **Automation branch (Stage 5A).** Execution Results and captured evidence (screenshots, traces, logs, HAR, framework reports) for this run. Stage 5A is a pure mechanical runner: this folder never contains a repair record. Where Stage 5H ran, it also holds that healing's **rerun cycles** — `ExecutionResults.rerun-N.md` and `artifacts_rerun-N/`, appended beside the original results, which are never edited (`module_architecture.md` §8.2). This is the one place a Stage 5H write lands outside a module.
- `reporting/` — **Automation branch (Stage 6A), terminal.** Final QA Report for this run. A Manual-only run has no `reporting/` folder, because the Manual branch self-reports in `manual_execution/` instead (`pipeline.md` §3.3).

**Where the relocated folders went:**

| Folder | Now lives at | Owned by |
|---|---|---|
| `context/` | `platform_core_data/modules/{module}/context/` | Stage 1 |
| `discovery/` (incl. `findings/`, `evidence/`) | `platform_core_data/modules/{module}/discovery/` | Stage 2 |
| `test_design/` | `platform_core_data/modules/{module}/test_design/` | Stage 3 |
| `automation/` | `platform_core_data/modules/{module}/automation/` — a standalone project, no longer a temporary working copy (`pipeline.md` §12.1) | Stage 4A |
| `self_healing/` | `platform_core_data/modules/{module}/healing/` — reasoning only; the rerun's results stay in `execution/` | Stage 5H |

**Retroactive note (2026-07-17, amended 2026-07-29):** an earlier version of this section had the Run Manager create the full folder skeleton upfront, before any Agent ran; that is replaced by the on-demand behavior above. Runs created under the earlier behavior had empty subfolders for stages they never reached, and those empty folders were removed (no run content was touched). Runs created between 2026-07-27 and 2026-07-29 legitimately hold `context/`, `discovery/`, `test_design/`, `automation/`, and/or `self_healing/`; **they are never rewritten** (§5.6), and a path resolver spans both layouts — the module workspace is checked first, then the run folder for pre-migration runs.

This Run Workspace is **the sole location for every *execution* artifact** the pipeline produces. There is no second, authoritative "current approved" copy of anything — approval flips the `status:` field in the artifact's own header and is recorded in the Run Manifest (`metadata/RunManifest.md`), per `pipeline.md` §7. The Run Manager organizes and monitors this view for history and archival; it does not own, and never writes, anything under `modules/` — that is the Module Manager's responsibility (`module_architecture.md` §6.6).

| `status` | The run's current value from the Execution Status enum (§8) |

Notes:
- A "version identifier" for a component that does not yet carry an explicit version tag is recorded as `unversioned` rather than invented — the Run Manager records what exists, it does not assign version numbers to specs that don't declare one.
- `title`, `description`, and `objective` are generated once, at run creation, from the same Scope/Target context as `folderName` (§5.3) — they are not re-derived or altered by later stages.
- `run.json` is updated in place as the run progresses (e.g., `status` changes, `finishedTime`/`duration` are populated on completion) — this is metadata *about* the run, not a project artifact whose content the Run Manager is forbidden from touching (§10).

# 8. Execution Status

Every run's status is exactly one of the following values at any given time:

| Status | Meaning |
|---|---|
| **Preparing** | The Run Manager has generated the run's folder name (§5) and is creating the Run Workspace and initial `run.json`; no Agent has started yet. |
| **Running** | At least one Agent stage is actively executing for this run. |
| **Paused** | Execution has been deliberately suspended (not a checkpoint — a manual pause) and is expected to resume. |
| **Waiting For Approval** | The run is stopped at one of the Human Review / Automation Approval checkpoints defined in `workflows_and_pipelines/pipeline/pipeline.md` §5, awaiting a reviewer decision. |
| **Completed** | The run reached its branch's terminal stage — `4M` for the Manual branch, `6A` (Reporting) for the Automation branch — and finished successfully. |
| **Failed** | The run stopped due to an error condition (e.g., an Agent could not complete its stage) rather than a deliberate pause or rejection. |
| **Cancelled** | The run was deliberately terminated before reaching a terminal stage, by explicit human decision. |

The Run Manager transitions a run's status based on mechanical signals (an Agent stage starting/finishing, a checkpoint opening per `workflows_and_pipelines/pipeline/pipeline.md` §5.3, an error being raised, an explicit pause/cancel instruction) — never based on its own interpretation of whether the Agents' output is good or correct.

# 9. Run Summary

Once a run reaches a terminal status (`Completed`, `Failed`, or `Cancelled`), the Run Manager publishes:

```
platform_core_data/runs/{{RUN_FOLDER}}/metadata/run_summary.md
```

**Header revision (2026-07-21, fields updated 2026-07-23):** for runs created under §5's current naming convention, `run_summary.md` opens with a `# Run Summary` heading followed by the run's descriptive identity fields (sourced verbatim from `run.json`, §7), before the pre-existing factual roll-up. Pre-existing runs' `run_summary.md` files are unchanged (§5.6).

`run_summary.md` must begin with:

```markdown
# Run Summary

- Folder Name: {folderName}
- Workflow: {workflow}
- Project: {project}
- Run Scope: {scope}
- Target: {target}
- Execution Purpose: {objective}
- Description: {description}
- Status: {status}
- Duration: {duration}
```

...then continue with the existing summary:

| Field | Description |
|---|---|
| Modules Executed | The module slugs this run executed against, and its `moduleScope` (§7) — a mechanical restatement of `run.json`, not a judgment about coverage adequacy |
| Visited Screens | Count of distinct screens/states captured in the executed modules' `discovery/` folders (a mechanical count of Explorer Skill discovery snapshots, not a judgment of exploration completeness) |
| Executed Agents | Which of the eight Agents ran during this run, in what order, and which branch(es) the run took |
| Generated Artifacts | A count/list of artifacts produced across the Run Workspace's subdirectories (§6), plus the module artifacts this run consumed (`moduleArtifactRefs[]`, §7) |
| Findings Count | Count of Finding evidence packages under the executed modules' `discovery/findings/` |
| Evidence Count | Count of evidence items across the executed modules' `discovery/` (screenshots/videos/logs/network captures) and this run's `manual_execution/`/`execution/` (screenshots/traces/logs/HAR/framework reports) |
| Screenshots Count | Count of screenshot files across the same locations (including any embedded within `discovery/findings/` evidence packages) |
| Videos Count | Count of video recordings across the same locations (including any embedded within `discovery/findings/` evidence packages) |
| Logs Count | Count of log files across the same locations |
| Coverage | The mechanical ratio of in-scope modules/screens actually visited (per Discovery Artifacts) against the Project Context's declared in-scope list — a count, not an assessment of whether that coverage was sufficient |
| Overall Status | The run's final value from the Execution Status enum (§8) — the same value as the opening block's `Status`, repeated here as it was in the pre-existing summary shape |

`run_summary.md` is a factual roll-up of counts and statuses drawn from what each Skill already produced, plus the descriptive identity fields already generated for `run.json` — it must never include an assessment of quality, correctness, or defect severity. Any such judgment belongs in the Explorer Skill's Findings Summary or the Reporting Skill's Final QA Report, not here.

# 10. Rules

1. The Run Manager never performs testing of any kind — it does not drive a browser, does not call an application, and does not execute test cases.
2. The Run Manager never interprets results — it counts and records what Agents produced; it does not decide whether those results are correct, acceptable, or a defect.
3. The Run Manager never changes the content of any project artifact produced by an Agent. It may organize where artifacts live within the Run Workspace (§6) and it may create/update its own metadata files (`run.json`, `run_summary.md`, the Active Run pointer (`current_active_run.json`, §5.7), and each refinement run's `lineage.json` (§5.9) — see those sections for their schemas; `run_summary.md`), but it must never edit, rewrite, or delete an Agent-produced artifact.
4. The Run Manager only prepares and coordinates execution — folder-name generation (§5, via `platform_core/tools/run_manager`), Title/Description generation (§7), workspace creation, metadata tracking, status tracking, and summary publication are its entire mandate.
5. The Run Manager must not bypass, shortcut, or auto-resolve any Human Review or Automation Approval checkpoint defined in `workflows_and_pipelines/pipeline/pipeline.md` §5 — reaching `Waiting For Approval` status is as far as it goes; only a human decision moves the run past that point.
6. The Run Manager must not read the PRD — per `workflows_and_pipelines/pipeline/pipeline.md` §6 Rule 4, only Stage 1 (Project Context Skill) is permitted to do so, and the Run Manager is not a stage.
7. **The Run Manager never writes under `platform_core_data/modules/`.** It reads the active-module pointer to record a run's module scope (§7) and reads module artifacts to count them for the Run Summary (§9). Creating a module, activating one, or recording a stage's progress against one is the Module Manager's mandate and nobody else's (`module_architecture.md` §6.5 Rule 3).

# 11. Inputs & Outputs

| | |
|---|---|
| **Inputs** | Project Name · Run Configuration (target environment, browser, resolution) · signals from each Agent stage marking start/completion/error · checkpoint state from `workflows_and_pipelines/pipeline/pipeline.md` §5.3 |
| **Outputs** | Run Workspace (§6) · `run.json` (§7, incl. the `targetRef` code-state anchor, §5.8) · `run_summary.md` (§9) · `current_active_run.json` (the Active Run pointer, §5.7) · `lineage.json` for a refinement run (§5.9) |

The Run Manager does not consume the PRD, the Project Context's business content, or any Agent's analytical output as *input to a decision* — it only observes that those artifacts exist, where they are, and what stage produced them.

# 12. Allowed Operations

- File system: create directories (Run Workspace), create/update the Run Manager's own metadata files (`run.json`, `run_summary.md`, `current_active_run.json` §5.7, `lineage.json` §5.9), read (not write) Agent-produced artifacts strictly to count/organize them.
- Read-only directory-listing and file-counting operations for compiling the Run Summary (§9).

**Not permitted:** browser automation tools, any tool that edits or deletes an Agent-produced artifact's content, any tool that mutates application data, and any tool that would let it act as an Agent (e.g., generating a Finding, test case, or report section).

# 13. Architecture

The Run Manager sits outside the eight-stage, two-pipeline Skill architecture defined in `workflows_and_pipelines/pipeline/pipeline.md`. It is the concrete specification of the "Pipeline Orchestrator (tooling, not a person)" role already named in that document's §5.3 and §9 Roles Summary.

```
                    ┌─────────────────────────────────────────┐
                    │              Run Manager                 │
                    │  (orchestration component, not an Agent) │
                    │                                           │
                    │  Generates run folder name (§5),          │
                    │  Run Workspace, run.json                  │
                    │  Tracks status through the run            │
                    │  Publishes run_summary.md at the end      │
                    └───────────────────┬───────────────────────┘
                                         │ provides workspace paths to
                                         ▼
   Stage 1        Stage 2        Stage 3        Stage 4M/4A     Stage 5A        Stage 5H        Stage 6A
Project Context → Explorer  → Test Design → Manual     → Automation → Automation → Reporting
   Agent            Agent        Agent      Execution      Agent      Execution     Agent
                                             Agent                      Agent
```

It orchestrates *execution* — allocating identity, workspace, and tracking to a run — but it is not considered an Agent, does not appear in the Pipeline Overview diagram in `workflows_and_pipelines/pipeline/pipeline.md` §3, and does not change that diagram's stage order, gates, or artifact contracts.
