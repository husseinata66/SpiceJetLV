## 1. Scope Summary

This is a **User Story** run covering **two stories together**:

- **US 8599 — [Admin] Search & Actions Branch.** A Super Admin or Admin searches Branch records by Branch Code, Branch Name, Country, State, City, and Status (Inactive / Active / Both), reads the results grid, and acts on a row: edit (navigates to Update Branch), approve (thumbs-up), reject (thumbs-down), and paginate through results.
- **US 8606 — [Admin] Update Branch.** A System Administrator updates an existing Branch across the same five field groups as Create (Branch Details, Email Configuration, Contact Info, Sales Configuration, Product Access Details), enters **mandatory Remarks**, and then submits for approval, approves, rejects, or cancels.

**The two were scoped into one run deliberately.** US 8599's edit-pen acceptance criterion asserts navigation to a pre-filled "Update Branch" page; without US 8606 that criterion would have to be stubbed or deferred against a screen no requirement described. The user supplied US 8606 specifically to close that dependency (recorded in `PRD_UserStories.md`'s provenance header, 2026-08-04). US 8606's own `Dependency` section names **Add Branch**, which this module already covers at Revision 5.

**This scope was previously declared out of scope, by name.** Revision 5 §3 listed "Search Branch (status-filtered search/list)" as excluded, with the reason *"owned by `branch` module's own future Search scope."* **This run is that scope.** The row moves from §3 to §2 below; the exclusion is closed, not overridden. Stage 2's `Coverage_Summary.md` recorded the same boundary from the other side — the Search Branch grid was visited as a single waypoint (`discovery/evidence/03-search-branch-grid.png`) with browser automation *"available, deliberately not used beyond the single waypoint screenshot."* That deliberate stop is where this run begins.

**Requirement authority for this run.** The default rule stands: where a business-authored User Story and `PRD.md` (reverse-engineered from automation, `Draft for business review`) disagree, **the User Story is authoritative** — it is business-written and more granular, and PRD.md's own §0/§17 provenance note states business intent wins. No application-primacy override analogous to the US-4222 directive has been granted for this run (§8).

**But the relationship to PRD.md is different here than it was for Create.** For US 8605, PRD.md's ORG-03 was *coarser* than the story. For US 8599 the reverse is true in places: the story describes the search and action surface in business terms, while PRD.md §6.1–§6.2 specifies the platform-wide cross-cutting behaviours that surface is an instance of — including literal contractual strings (`No data has been found!`, `Showing <n> results of <m> results`) and structural rules (Status and Approval Status are **distinct** columns, XC-07) that US 8599 does not restate. These are **[V]**-tagged (verified by an automated assertion) and are treated as corroborating detail, not as a competing requirement. Where a `[V]`-tagged cross-cutting rule and the story are silent-vs-specific rather than contradictory, both are carried into Test Design.

**On XC-06 and this run's action scope — corrected at Revision 8.**

PRD.md XC-06 states an approver *should not be able to approve their own change*, tagged **[I]** (inferred from `LoginAsSuperAdmin()` appearing consistently before approval steps) and explicitly flagged as **not asserted** — it is PRD.md's own open question `OQ-1`. US 8599 and US 8606 are the first in-scope stories that put approve and reject on the critical path, which makes this the first run where XC-06 is directly reachable.

**Revision 6/7 recorded that XC-06 was untestable without a second account. That was wrong, and is corrected here.** A single account is *precisely* the configuration that exercises self-approval: create a Branch as `odeysysadmin`, then attempt to approve that same Branch as `odeysysadmin`. The maker and checker being identical **is** the self-approval scenario. Either outcome is a real result:

| Observed | Conclusion |
|---|---|
| The approval succeeds | Self-approval is **not** enforced — XC-06 is unimplemented. A definitive answer to PRD.md `OQ-1`, and a governance finding in its own right |
| The approval is blocked | Self-approval **is** enforced — XC-06 confirmed, and PRD.md's **[I]** tag can be upgraded on evidence |

**Two limits the directive does not remove, and which must not be presented as covered:**

1. **No control case.** With one account there is no way to demonstrate that approval by a *different* user succeeds. So "the approval was blocked" cannot be distinguished from "approval is broken for everyone." A blocked result therefore needs its message and behaviour captured as evidence (per XC-03, a blocked self-approval should still be distinguishable from a generic failure), and reported as *self-approval appears blocked* rather than *self-approval is blocked*.
2. **No role-differentiated observation.** `odeysysadmin` holds Super Admin privileges regardless of which actor it is standing in for. Whether a genuinely lower-privileged Admin sees the same grid columns, the same row actions, or the same enabled/disabled icon states **cannot be observed from this account** — a privileged account cannot demonstrate an unprivileged view. Any US 8599 acceptance criterion that depends on *"what an admin sees"* as distinct from *"what a Super Admin sees"* stays untested this run and is recorded as such (RISK-BR-6).
