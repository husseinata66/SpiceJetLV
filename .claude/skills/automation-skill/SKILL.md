# 1. Skill Name

**Automation skill** (Automation Engineering skill) — v3

# 2. Purpose

The Automation skill transforms the **approved Stage 3 Manual Test Suite** into a **production-quality automation project** — not merely a collection of isolated scripts. It automates exactly the test cases in the run's scope — no more, no less — respecting the business rules already reconciled into the Project Context, verifying every selector live against the running application before emitting it (§11A), reusing whatever automation already exists before generating anything new, and being explicit about anything it could not safely, reliably, or confidently automate.

**It does not wait on manual validation.** The Automation branch is independent of the Manual branch (`pipeline.md` §3.3): this stage's correctness comes from its own live verification against the build the suite will run on, which is stronger and more current evidence than a manual pass on an earlier build.

**Its responsibility ends the moment the automation package has been successfully generated.** It never executes the suite against any environment and never reports pass/fail results — that is exclusively Stage `5A`'s responsibility. **It also never repairs**: diagnosing and fixing a failed test is Stage `5H`'s job (`self-healing-skill`), and only on explicit human invocation. This boundary is absolute — generating code, running code, and repairing code are three different stages.

**Driving the browser to *verify* a selector is not executing the suite** (§11A). Verification confirms a locator resolves and a flow is reachable; execution runs the generated tests and produces results. The first is this stage's own grounding work, the second is Stage `5A`'s.

**The project's architecture is not re-invented per run.** For Java/SHAFT UI automation, this skill generates into one approved Maven structure with a fixed responsibility separation — Page Classes, dedicated Locator Classes, Test Classes, shared fixtures, externalized JSON test data, a reused Driver Factory, and a bounded set of technical utilities (§8). Anything beyond those areas is an optional abstraction that must be justified by evidence, never generated because it might be useful later. For any other framework or system shape, the same principles apply in that stack's own approved structure (§8.12).

This skill designs and generates a project; it does not execute one.

# 3. Responsibilities

- **Consume only approved artifacts** (§4) — Project Context, the Manual Test Suite (**scope and content**), Requirement Traceability Matrix, Coverage Report, Discovery Artifacts, Findings, and Evidence Packages, every one cleared at its own pipeline checkpoint. **Never a Manual Execution artifact** (`pipeline.md` §3.3).
- **Verify every selector and flow live, headless, before emitting it** (§11A) — and disclose, never guess, whatever could not be verified.
- **Consult both shared knowledge bases before generating** (§11B) — reuse confirmed locators, and pre-empt known failure modes in the first draft.
- **Detect brownfield vs. greenfield automatically, and present a Target Write Plan for approval** (§11C) — never prompt for what can be detected, never write to the Target Project before the plan clears.
- **Self-review within a bounded iteration and time budget, disclosing every unsatisfied check** (§15A).
- **Never read the PRD directly** — only Stage 1 (Project Context skill) is permitted to, per `workflows_and_pipelines/pipeline/pipeline.md` §6 Rule 4.
- **Produce a complete Automation Plan (§5) before any code generation begins.** No script, page object, or configuration file is written until the plan is finished.
- **Detect the target automation framework from the approved Project Context — never assume one** (§6), and select the most appropriate framework using explicit, justified criteria (§7), treating SHAFT Engine as a first-class option (§8) alongside Playwright, Selenium, Cypress, Appium, REST Assured, and any other framework the Project Context or existing project may specify.
- **Generate every Java/SHAFT UI package into the platform's one approved Maven structure, with its fixed responsibility separation** (§8) — Page Classes and their dedicated Locator Classes under `src/main/java/AdminPages/`, Test Classes under `src/test/java/AdminPages/`, shared fixtures under `src/test/java/utilities/`, JSON test data under `src/test/resources/`, a reused Driver Factory, and no generic root package beside it. This is platform-level strategy, not a per-module choice.
- **Keep the architecture simple, and justify every optional abstraction with evidence** (§8.11) — never generate a workflow, service, assertion class, Component Object package, data factory, builder, adapter, module-specific base page, or one-method wrapper as a default layer.
- **Perform the blocking Architecture Review before declaring generation complete** (§15.1) — recording file, method, current and expected responsibility, correction made, remaining exception, and approval requirement for every violation, and never reporting `Passed` while an unapproved violation remains.
- **Report, never silently refactor, an existing package's architecture deviations** (§8.13) — preserve valid conventions and behavior, and route every proposed structural move through the Target Write Plan for individual approval.
- **Inspect any existing automation project before generating anything new** (§9), and treat it as a reusable knowledge base (§11) — reuse before generating is not a preference, it is the default behavior.
- **Group approved test cases into logical automation suites organized around business workflows**, not individual pages or screens (§10), with shared setup, teardown, fixtures, components, utilities, and test data per suite.
- **Assign every test case in the run's scope exactly one Automation Decision** — Reuse Existing Automation, Generate New Automation, Partially Automatable, or Manual Only (§13) — each with an explicit justification, never a silent omission.
- **Generate only maintainable automation** — modular, DRY, readable, reusable, maintainable, versionable (§14) — preferring composition over duplication.
- **Perform a Self Review pass before declaring generation complete** (§15), checking naming consistency, duplicate code, broken references, and missing reusable assets/page objects/utilities/test data, and producing recommendations wherever improvements are identified.
- **Maintain the full traceability chain** — Requirement → Discovery → Finding → Evidence → Manual Test Case → Automation Script (§12) — on every generated asset.
- Report any test case that cannot be automated safely — explicitly, by ID, with a reason — rather than silently dropping it or forcing a workaround.
- Never invent missing business logic. If a test case or the Project Context does not fully specify expected behavior for a scenario, this skill flags the case as not fully automatable (§13) rather than guessing at the missing logic.
- Never modify an approved manual test case to make it more automatable — a test case that needs to change is a Stage 3 concern, escalated as a discrepancy, not silently rewritten here.
- Never overwrite an existing reusable asset (page object, utility, fixture, component) without explicit approval — extend or compose around it instead, or flag the conflict for a human decision.
- **Never execute the generated automation** — running it is the Automation Execution skill's responsibility, exclusively.
- **Adapt automation strategy to the run's Run Scope Type** (§23) — an Entire Project generation pass, a single Feature's suite, and a Bug's regression-script-only scope are different activities at different breadth, not one default approach applied uniformly.
- **Apply a named, prioritized Locator Strategy with fallback and recovery recommendations** (§24) — never generate a brittle, single-strategy selector where a more stable and a fallback option both exist.
- **Produce output conforming to the Standard Output Contract** (§25), including the Automation Summary (§16), so the Automation Execution skill never has to interpret free-form prose to find what it needs.
- **Recognize named Stop Conditions** (§26) and, rather than halting the entire run over one blocked test case, recommend the smallest missing prerequisite needed to unblock it (§27) while continuing to generate automation for every other unblocked test case.
- **Verify handoff completeness before concluding a run** (§28) — confirm every input the Automation Execution skill's own specification declares it needs is actually present, specific, and unambiguous, not merely assumed.

| Requirement Traceability Matrix | Secondary | Required, must be `Approved` | `platform_core_data/modules/{{MODULE_SLUG}}/test_design/TraceabilityMatrix.md` — carries the Requirement/Discovery/Finding/Evidence references this skill must propagate onto each Automation Script (§12) |
| Coverage Report | Secondary | Required, must be `Approved` | `platform_core_data/modules/{{MODULE_SLUG}}/test_design/CoverageReport.md` — informs which test cases and Findings are already known to be Uncovered/exceptions, so this skill doesn't attempt to automate what Stage 3 already excluded |
| Discovery Artifacts | Secondary | Required, must be `Approved` | `platform_core_data/modules/{{MODULE_SLUG}}/discovery/*.md` — **behavioural context only.** Discovery deliberately carries **no selectors and no DOM captures** (`pipeline.md` §3.5), so a selector is never sourced here: it is verified live against the running application in §11A. Never a source of business logic. |
| Findings | Secondary | Required if any exist, must be `Approved` | `platform_core_data/modules/{{MODULE_SLUG}}/discovery/findings/Findings_Summary.md` and each `FINDING-{ID}_{ShortName}/metadata.md` — used to carry Finding Reference through to the Automation Script that regress-tests or exploratory-tests it |
| Evidence Packages | Secondary | Required wherever a test case's Finding Reference is populated, must be `Approved` | `platform_core_data/modules/{{MODULE_SLUG}}/discovery/findings/FINDING-{ID}_{ShortName}/` — cited by reference on the resulting Automation Script; never copied wholesale into generated code |
| Existing Automation Package(s) | Contextual | Optional — present if one or more prior automation efforts exist | **A project holds exactly one authoritative Automation Package per framework** (v8) — e.g. `tests_SHAFT/` and `tests_Playwright/` both under `platform_core_data/modules/{{MODULE_SLUG}}/automation/`, tracked in that project's `AutomationPackages.md` registry (§19), one row per framework. Multiple *different* frameworks may coexist; never two competing packages within the same framework. This skill reads the registry in full, inspects each framework's one project per §9, and treats it as a reusable knowledge base per §11, before the Framework Decision Gate (§31) asks whether to extend the existing project, start one for a framework that doesn't have one yet, or (rare, explicit) reset one from scratch. |

**This skill must never read the PRD directly** (`platform_core_data/knowledge_base/PRD.md` or equivalent) — only Stage 1 is permitted to, per `workflows_and_pipelines/pipeline/pipeline.md` §6 Rule 4. If a test case's specification is genuinely incomplete, that is reported as a gap (§13, "Partially Automatable" or "Manual Only") rather than a reason to independently consult the PRD or raw Discovery Artifacts for missing business logic.

**This skill must never read a Manual Execution artifact** (`pipeline.md` §3.3). The Manual Execution Results, its CSV, and its QA Report are the other branch's deliverables: a manual pass is not evidence that automation will work, and a manual failure is not evidence that a test should not be automated. This stage grounds its correctness in its own live verification (§11A), which is evidence about the build the suite will actually run against.

**Waiting on the Manual branch is never a precondition here.** A run may generate automation without any manual execution ever having happened, and that is a complete, valid Automation-branch run — not a degraded one requiring disclosure.

# 5. Automation Planning Engine

**Before generating any automation asset, this skill must produce a complete Automation Plan.** No code generation of any kind — no script, page object, fixture, or configuration file — begins before this plan is finished and internally consistent.

The Automation Plan must include:

- **Target Framework** — the framework selected per §6–§8, with its justification
- **Target Language** — the programming language the framework will be authored in
- **Project Architecture** — the overall structure of the automation project. **For Java/SHAFT UI automation this is not an open choice: it is §8.1's approved Maven structure**, and the plan states it by reference rather than re-deriving one. For any other framework or system shape, it is that stack's own approved structure, subject to §8.12's principles.
- **Design Pattern** — the specific pattern(s) in use (e.g., Page Object Model, Screenplay, Fixture-based composition). For Java/SHAFT UI: Page Class + dedicated Locator Class + Test Class + Fixture + JSON test data (§8.2–§8.6).
- **Responsibility Map** — for every asset the plan intends to create or modify, the responsibility area of §8.1 it belongs to (Page · Locator · Test · Fixture · Driver Factory · Generic Class · Utility · JSON test data · configuration), and its target path. An asset with no stated area is an incomplete plan field.
- **Optional Abstractions** — every abstraction outside §8.1's default areas, each with its §8.11 justification: which of the two grounds it rests on (authoritative existing/Reference project requirement, or proven duplication in several named places), why maintenance is simpler with it, and why its responsibility cannot be placed cleanly in the approved structure. **An abstraction listed with no justification is an incomplete plan, held to the same standard §7 applies to an unjustified framework choice.** Where none are proposed, the field says `None` rather than being omitted.
- **Architecture Deviations** — for a brownfield package, every deviation of the existing structure from §8.1–§8.11, each classified `Preserved (approved convention)` · `Correction proposed in Target Write Plan` · `Reported, no action` (§8.13). Never a silent refactor, and never a silent omission.
- **Planned Automation Suites** — the business-workflow-organized suites from the Suite Planning Engine (§10)
- **Existing Assets** — everything already reusable, discovered per Existing Framework Analysis (§9)
- **Assets To Generate** — what must be newly authored, and why nothing existing covers it
- **Assets To Reuse** — the specific existing assets this plan intends to reuse, and where
- **Estimated Automation Coverage** — a projected percentage of approved test cases expected to receive a Reuse/Generate decision (§13) versus Partially Automatable/Manual Only, before generation actually happens
- **Known Manual Tests** — test cases already known, before generation, to require `Manual Only` (e.g., visual judgment calls, exploratory-test dispositions carried from Test Design)
- **Blocked Tests** — test cases that cannot proceed to a decision yet because a prerequisite (environment, credential, upstream artifact) is missing
- **Risks** — risks to the automation effort itself (e.g., a flaky shared environment, an under-specified requirement likely to need rework)
- **Assumptions** — anything this plan assumes to be true that isn't independently confirmed (e.g., "assumes the existing Page Object for Login remains stable for the duration of this suite's generation")

The Automation Plan is itself a required output (§16) and is written first, in full, before any other artifact in this stage.

# 6. Framework Detection

This skill determines the target automation technology from the approved Project Context. **It must never assume a framework.**

Supported automation frameworks include, but are not limited to:

- Playwright
- SHAFT Engine
- Selenium
- Cypress
- Appium
- REST Assured
- Postman (API collections/environments, where a project's automation is Postman-based rather than a full code framework)

This list is explicitly extensible and must never be treated as exhaustive — a Project Context or an existing automation project may specify or already use a framework not listed here, and this skill must accommodate it rather than forcing a fit into one of the frameworks named above.

**Playwright must never be treated as the default.** It appears first in the list above and throughout this document's examples purely for illustrative consistency — that is a documentation convenience, not a selection preference. This skill selects a framework only via §7's precedence rules (explicit Project Context statement → existing project's framework → criteria-based selection), and an example elsewhere in this specification using Playwright must never be read as license to prefer it absent one of those three grounds.

If the Project Context does not specify a framework and no existing automation project exists to infer one from, this skill halts and reports the gap rather than picking a framework unilaterally.

**Discovery technology is never Automation technology (v4).** Which tool Stage 2 (Explorer skill) happened to use for Browser Automation — Playwright, a Playwright MCP server, or anything else — is Discovery tooling, scoped entirely to §8.1 of `.claude/skills/explorer-skill/SKILL.md`. It carries **zero weight** in this skill's framework choice and must never be cited as a reason, partial reason, or tiebreaker for selecting an automation framework. A project whose Framework Configuration names SHAFT (or any other framework) uses that framework's real toolchain (for SHAFT: Java, TestNG, Allure — §8) regardless of which browser-automation tool Discovery happened to use. Conflating the two — e.g., generating Playwright automation because Playwright was already open for Discovery — is a specification violation under this revision, not a harmless convenience. See §31 (Framework Decision Gate).

# 7. Framework Selection

Where a specific framework is not already dictated (see below), the Automation skill selects the most appropriate automation framework based on the approved Project Context, using these criteria:

- Existing automation framework (if one is already in use in this project)
- Existing project structure
- Technology stack
- Programming language
- Application type (Web, API, Mobile, Desktop)
- Team standards (as stated in the Project Context or run configuration)
- Existing reusable automation assets

Rules, in order of precedence:

1. **If the Project Context explicitly specifies a framework, this skill must use it.** No selection process overrides an explicit instruction. This still requires running the Framework Decision Gate (§31) before generating anything — an explicit Project Context statement tells this skill *which answer to expect*, it does not license skipping the question. If the human confirms the stated framework, proceed; if the human asks for something else, that supersedes the Project Context statement (the human's live decision governs over a possibly-stale document, but the disagreement is itself surfaced, never silently resolved either way).
2. **A project holds exactly one authoritative Automation Package per framework (v8)** — the repository stores one project per framework it uses; it does not bind a project to a single framework overall, but it never holds two competing, independent packages *within* the same framework either. "Reuse before generating new" (§9/§11) applies within that one project, never split across parallel packages that fragment the same framework's coverage. Per §31, this skill enumerates every existing framework's project, and asks — per §31.6's Human Decision Principle, never inferred — whether to extend the existing one, start a project for a framework that doesn't have one yet, or (rare, explicit) reset a framework's project from scratch.
3. Only when neither of the above applies does this skill select a framework — but never autonomously. The criteria list above informs a **recommendation** this skill presents to a human via the Framework Decision Gate (§31); it is never used to silently pick a framework and proceed, no matter how clear-cut the criteria look.

**The selected framework must always be justified in the Automation Plan (§5)** — a framework choice with no stated justification is incomplete. The justification records both the criteria that informed any recommendation *and* the human's actual decision at the Framework Decision Gate (§31) — never a recommendation alone, presented as if it were the decision.

# 8. SHAFT Engine Support and the Java/SHAFT UI Automation Architecture

**SHAFT Engine is a first-class automation framework for this skill — not a fallback, and not treated as a lesser-supported option.**

When SHAFT Engine is selected (per §6–§7), this skill generates automation that follows SHAFT Engine best practices and uses the framework's own facilities rather than reimplementing them: TestNG as the runner, Allure as the reporting layer (wired by SHAFT itself, never re-authored per test), SHAFT's driver lifecycle, SHAFT's fluent assertion/validation API, SHAFT's configuration properties, and SHAFT's data-driven support where a test case's Test Data implies variants.

**This skill must avoid generating generic Selenium code when SHAFT Engine is selected.** SHAFT Engine wraps and extends Selenium/Appium/REST Assured with its own conventions and utilities; falling back to raw, unwrapped Selenium calls when SHAFT is the selected framework is a specification violation, not a harmless simplification.

**§8.1–§8.13 below are the platform's Automation Strategy for Java/SHAFT UI automation.** They are mandatory, they are not limited to any one module, and they are not re-decided per run. Every other active section of this specification — Planning (§5), Existing Framework Analysis (§9), Suite Planning (§10), the Knowledge Base (§11), the Target Write Plan (§11C.4), Code Generation Standards (§14), Self Review (§15/§15.1), Outputs (§16), the Standard Output Contract (§25), and the Reference Project rules (§32.5) — is read subject to this section.

## 8.1 The approved Maven structure — mandatory, platform-wide

**Every Java/SHAFT UI automation package this skill generates or extends uses exactly this structure:**

```text
src/
├── main/
│   ├── java/
│   │   ├── AdminPages/           Page Classes + their matching Locator Classes
│   │   ├── Drive_Factory/        driver creation, browser configuration, driver lifecycle
│   │   ├── Generic_Classes/      genuinely project-wide, single-responsibility classes
│   │   └── utilities/            cohesive technical utilities
│   └── resources/
│       └── properties/           configuration
│
└── test/
    ├── java/
    │   ├── AdminPages/           Test Classes, mirroring the Page Class organization
    │   ├── DBs_Query_Execution/  authorized database query execution
    │   ├── org/example/          the framework's own entry/scaffold package
    │   └── utilities/            shared fixtures — setup and cleanup only
    └── resources/                JSON test data, by module or business scope
```

**Every path in §8 is relative to the automation project's own root — never to the Target Project root.** That root is always resolved, never assumed: `<targetRoot>/<automationRoot>` for a Target Project write (§11C.4, from `platform.config.json` and `detectTestDirs`), or the module automation project / Workspace Automation Baseline (`automation_lifecycle/automationRoot.js`). `src/main/java` and `src/test/java` are Maven's own source sets inside that resolved project; where the team's existing project differs, §8.13 governs (report the deviation, refactor nothing silently).

**Responsibility separation happens inside this structure, never by adding root packages beside it.** These generic root packages must never be created for a Java/SHAFT UI package, and an existing structure must never be replaced by them:

```text
pages/   locators/   tests/   fixtures/   workflows/   assertions/   services/   data/
```

A responsibility that appears to need one of them already has a home above. If it genuinely does not, that is a repository-structure question for a human (§31.6) — never a new top-level package this skill invents.

## 8.2 Page Classes — `src/main/java/AdminPages/`

Organized by application area and module:

```text
src/main/java/AdminPages/Admin/Agency/
├── CreateAgency_Page.java
├── SearchAgency_Page.java
└── UpdateAgency_Page.java
```

**Each Page Class represents one page or screen.**

| A Page Class **may** contain | A Page Class **must not** contain |
|---|---|
| Page-specific UI actions | Locator declarations |
| Page-specific state-reading methods | Test assertions |
| Page-specific waits and synchronization | Test setup or teardown |
| Navigation actions originating from that page | Test-data provisioning, or static test data |
| Calls to its matching Locator Class | API or database preparation |
| | Test orchestration |
| | Methods unrelated to that page |
| | Shared fixtures |
| | Generic containers of unrelated methods |

Representative method shapes:

```java
enterAgencyName(String name)
selectCountry(String country)
clickSearch()
clickSave()
openForUpdate(String code)
isSuccessMessageVisible()
validationMessageFor(String fieldName)
codesOnCurrentPage()
```

**Page Classes expose actual state; Test Classes decide whether the result passes or fails.**

```java
// Allowed — reports state
public boolean isSuccessMessageVisible() { ... }

// Not allowed — decides the verdict
public void assertSubmissionSucceeded() { ... }
```

## 8.3 Locator Classes — one per Page Class, same package

**Every Page Class has its own dedicated Locator Class, in the same application/module package:**

```text
src/main/java/AdminPages/Admin/Agency/
├── CreateAgency_Page.java
├── CreateAgency_Locators.java
├── SearchAgency_Page.java
├── SearchAgency_Locators.java
├── UpdateAgency_Page.java
└── UpdateAgency_Locators.java
```

A Locator Class contains **locator definitions only** — never UI actions, assertions, test data, setup or cleanup, business logic, test flow, or unrelated driver behavior.

Locator naming convention, applied whenever it does not conflict with an approved existing convention (§8.13):

| Prefix | For |
|---|---|
| `Btn_` | Buttons |
| `Txt_` | Text fields |
| `Lst_` | Dropdowns and lists |
| `Icn_` | Icons |
| `Rbtn_` | Radio buttons |
| `Cbox_` | Checkboxes |
| `Dpick_` | Date pickers |

```java
Btn_Save   Txt_AgencyName   Lst_Country   Icn_Update   Rbtn_Active   Cbox_ProductAccess   Dpick_ExpiryDate
```

Mandatory rules:

- **No locators inside Test Classes.**
- **No locator declarations inside Page Classes.**
- **No duplicated locator definitions** — each locator has exactly one authoritative definition.
- Page methods reach the DOM only through their matching Locator Class.
- **Selector Verification traceability (§11A.4) is preserved when a locator is moved or reused** — relocating a verified locator into a Locator Class carries its verification record with it; it does not reset it.
- **A verified locator is never replaced merely for naming or style.** A rename that would discard live-verified evidence is a §11A.5 disclosure, not a cleanup.

## 8.4 Test Classes — `src/test/java/AdminPages/`

Same application/module organization as the Page Classes:

```text
src/test/java/AdminPages/Admin/Agency/
├── CreateAgency_Admin_TC.java
├── SearchAgency_Admin_TC.java
├── UpdateAgency_Admin_TC.java
└── AgencyActions_Admin_TC.java
```

| A Test Class contains **only** | A Test Class **must not** contain |
|---|---|
| The readable test flow | Locators |
| Calls to Page methods | Direct driver or element interactions |
| Calls to shared setup/cleanup when required | Hardcoded or static test data |
| Assertions | Page-specific waits or retries |
| Test metadata | Reusable UI helper methods |
| Test Case traceability (§12) | Duplicated setup or cleanup |
| Reading required test data from JSON | Generic utility methods, or complex implementation logic |

- **A test may call multiple Page Classes directly** to express a multi-page scenario.
- **Interacting with more than one page is never a reason to generate a workflow or service class** (§8.11).
- **Simple, test-specific assertions stay inside the Test Class.** A shared assertion *class* is not a default layer (§8.11); an assertion used by many tests is satisfied by asserting on a Page Class's state-reading method, not by wrapping it.

## 8.5 Shared fixtures — `src/test/java/utilities/`

```text
src/test/java/utilities/
├── AuthenticationFixture.java
├── AgencyFixture.java
└── BranchFixture.java
```

Fixtures are allowed **only** for: authentication/session preparation · reusable test preconditions · creating prerequisite records · authorized API or database setup · reusable cleanup · rerun safety and idempotency · setup shared by more than one test.

Fixtures must **not** contain: normal test steps · assertions · page locators · complete business scenarios · unrelated shared methods · one-method wrappers around Page actions.

- **Prefer one cohesive fixture per module.** Split only on clearly separate responsibilities that have become hard to maintain — never pre-emptively.
- **Page Classes must never depend on fixtures** (§8.10).
- Where the Application Context (§4) states a fixture build order, fixtures follow it rather than re-deriving prerequisites per test.

## 8.6 JSON test data — `src/test/resources/`

Organized by module or business scope:

```text
src/test/resources/
├── agency/
│   ├── create-agency.json
│   ├── search-agency.json
│   └── update-agency.json
└── branch/
    ├── create-branch.json
    ├── search-branch.json
    └── update-branch.json
```

**Test data is JSON-driven.** It is never hardcoded inside a Test Class, Page Class, Locator Class, Fixture, utility, or base class.

- **Test data** means: names, codes, countries, valid values, invalid values, boundary values, search values, and expected messages used by test scenarios.
- **Not test data**, and allowed to stay in code: technical constants, configuration keys, framework enums, and other non-test-data constants.
- **Never store a credential, secret, token, or private environment value in a committed JSON file.** Credentials continue to use the approved secure configuration mechanism (`platform_core/tools/browser_driver/README.md` §4 and the project's own environment-variable contract) — this rule is unchanged and is not weakened by JSON-driven test data.
- **Use the smallest existing JSON-reading mechanism.** Do not generate builders, factories, providers, or model layers to read a JSON file (§8.11).

## 8.7 Drive Factory — `src/main/java/Drive_Factory/`

Owns driver initialization, browser configuration, driver lifecycle, and approved execution-mode configuration.

It must not contain page actions, locators, business logic, test data, module-specific setup, assertions, or fixtures.

**Reuse the existing Driver Factory. Never generate a competing one.** For SHAFT specifically, this area configures SHAFT's own driver lifecycle rather than replacing it.

## 8.8 Generic Classes — `src/main/java/Generic_Classes/`

For genuinely project-wide classes with **one clear responsibility** — JSON reading, configuration reading, shared technical data representation, narrow framework-level behavior.

**Not a dumping ground.** These names must never be generated:

```text
SharedMethods   CommonMethods   GeneralHelper   BaseUtils
```

Module-specific behavior stays in its Page Class, Test Class, Fixture, Locator Class, or JSON data.

## 8.9 Utilities — `src/main/java/utilities/`

For cohesive technical utilities only — e.g. `PaginationHelper.java`, `FileUtility.java`, `DateUtility.java`.

A utility must have one clear technical responsibility, be genuinely reusable or required by the approved existing structure, contain no business behavior, contain no test assertions, contain no module-specific setup, and not duplicate framework-native behavior without a stated justification.

**Never generate a utility for possible future use.**

## 8.10 Default dependency direction

```text
Test Classes            →  Page Classes  →  Page-specific Locator Classes
Test Classes            →  Fixtures (setup and cleanup only)
Test Classes / Fixtures →  JSON test data
Page Classes / Fixtures →  approved Generic Classes or Utilities, when required
Drive Factory           →  driver lifecycle only
```

**Prohibited, without exception:**

| Prohibited edge | Why |
|---|---|
| Page → Test | A page cannot depend on who is testing it |
| Page → Fixture | Setup is the test's concern, never the page's |
| Locator → Page / Test / Fixture | A locator definition depends on nothing |
| Fixture → Test | Setup cannot depend on the test it prepares for |
| Driver Factory → module-specific behavior | The driver layer is module-agnostic |
| Utility → module-specific Test or Page behavior | A utility that knows a module is not a utility |
| Any circular dependency | — |

## 8.11 Keep the architecture simple

**These are never generated as default layers:**

```text
Workflows · Services · Assertion classes · Component Object packages · Data factories
Builders · Technical adapters · Module-specific BasePage classes · One-method wrapper classes
```

An optional abstraction is allowed **only** when all of the following hold:

1. The authoritative existing or Reference project already requires it (§8.13, §32.5); **or** proven duplication exists in several places;
2. The abstraction clearly makes maintenance simpler;
3. Its responsibility cannot be placed cleanly anywhere in §8.1's structure.

**Every optional abstraction is justified in the Automation Plan (§5).** Possible future reuse is never sufficient justification. **No empty folder is created for an optional abstraction.**

**The simplicity requirement, stated as a test:** a tester modifying a normal UI Test Case should usually need to open only —

1. the Test Class; 2. the relevant Page Class; 3. the matching Locator Class, if the locator changed; 4. the JSON file, if the data changed; 5. the Fixture, only if setup or cleanup changed.

A normal Test Case that fails this test is a §15.1 blocking finding.

## 8.12 Framework and system-shape scope

**§8.1's exact Maven structure governs Java/SHAFT UI automation, and only that.** It must never be forced onto API automation, mobile automation, messaging systems, batch systems, cloud automation, or a different framework with its own explicitly approved project structure.

For every other framework or system shape, the same **principles** still apply, expressed in that stack's own idiom:

- The test flow stays readable.
- Interface actions are separated from tests.
- Element or endpoint definitions are not duplicated.
- Test data is externalized.
- Setup and cleanup are reusable.
- Unnecessary layers are not generated.

**An approved existing or Reference project architecture takes precedence when it is explicitly documented** (§8.13, §32.5, §34.5).

## 8.13 Brownfield handling for an existing Java/SHAFT package

- **Inspect the authoritative existing structure first** (§9) — before planning a single file.
- **Preserve valid project conventions**, including naming conventions this section would otherwise suggest changing.
- **Report every deviation** from §8.1–§8.11 in the Automation Plan (§5) and the Target Write Plan (§11C.4). Reporting is mandatory; refactoring is not authorized by it.
- **Never silently perform a large architecture refactor.** A structural move is proposed in the Target Write Plan and individually approved (§11C.4 rule 3), exactly like any other modification of a file the team owns.
- **Never add new complexity because similar complexity already exists.** An existing `SharedMethods`-style class is not permission to add a second one.
- **Preserve Test Case IDs, steps, expected results, and behavior** through any move. A relocation that changes what a test asserts is not a relocation (§15A.4).
- **Record every proposed move and deletion in the Target Write Plan** (§11C.4) — including the deletion rules in §11D.3 that already forbid silent removal.
- **Respect lifecycle and ownership rules** — `.module_automation_state.json` (§11D.4), `.baseline_ownership.json` (§11D.4a). A structural move that touches a `foreign` path is a hard stop, not a refactor.
- **Existing style is a naming guide, never permission to violate a responsibility boundary.** The §8.10 dependency prohibitions and the §15.1 blocking checks apply to newly generated and newly modified code regardless of how the surrounding code is written. Where the existing code already violates them, that is a reported deviation for a human to decide on — not a standard the new code inherits.

# 9. Existing Framework Analysis

Before generating any new automation, this skill inspects the project's one existing Automation Package for the resolved framework (per §4's "Existing Automation Package(s)" input and the project's `AutomationPackages.md` registry, §19/§31) — and, if the project uses more than one framework, each of those frameworks' own one project independently. As of §33.2, "an existing Automation Package" means the **Workspace Automation Baseline**, copied wholesale into this run's own working copy at Working Copy Creation (`workflows_and_pipelines/pipeline/pipeline.md` §12.3) — never a prior run's folder inspected in place, and never a location this skill reads from without first having copied it in. For each package found, it detects:

- Existing Test Scripts / Test Classes
- Existing Page Objects / Page Classes
- **Existing Locator Classes**, and any locator defined outside one
- Existing Utilities
- Existing Fixtures
- Existing Test Data, and where it lives (externalized vs. hardcoded in Java)
- Existing Helpers
- **Existing Driver Factory** — the one that must be reused rather than competed with (§8.7)
- **Existing Generic Classes**
- Existing Folder Structure — **and, for a Java/SHAFT UI package, how it compares to §8.1's approved Maven structure, area by area**
- Existing Naming Conventions — including any locator-prefix convention already in force (§8.3)
- Existing Reporting Solution
- Existing Build Tool

**The authoritative existing structure is inspected before anything is planned** (§8.13). This inspection is what makes the plan's Responsibility Map and Architecture Deviations fields (§5) answerable; producing either without it is guessing.

**Reuse before generating.** The output of this analysis feeds directly into the Automation Plan's "Existing Assets" field (§5) and into the Automation Knowledge Base search performed before every individual generation decision (§11).

**Deviations are reported, never silently refactored.** Every place the existing structure differs from §8.1–§8.11 is recorded in the Automation Plan's Architecture Deviations field, with its §8.13 classification. Inspecting a deviation is not authorization to correct it: a structural move is proposed in the Target Write Plan and approved file by file (§11C.4).

If no existing automation project exists, this section's analysis is trivially empty, and the Automation Plan records that explicitly ("no existing automation project found — greenfield generation") rather than silently skipping the step. A greenfield Java/SHAFT UI package is scaffolded directly to §8.1's structure, with no responsibility area created empty (§8.11).

# 10. Suite Planning Engine

This skill analyzes all approved test cases and groups them into logical automation suites. **Grouping must follow business workflows, not individual pages.**

Examples of business-workflow-organized suites:

- Login Suite
- Employee Suite
- Leave Suite
- Recruitment Suite

A suite organized around a single page (e.g., a suite that is just "Employee List Page tests," disconnected from the Add Employee / Employee Detail tests that form the same business workflow) is the wrong shape and must not be produced — the workflow, not the screen, is the organizing unit.

**A suite is a logical grouping of tests, not a folder layer and not a class.** This is the distinction that keeps §10 and §8 consistent, and it is stated explicitly so neither is read as licensing the other:

| A suite **is** | A suite is **not** |
|---|---|
| A named grouping of Test Classes that cover one business workflow | A `workflows/` or `services/` package (§8.1 forbids both) |
| Expressed in the framework's own grouping mechanism — for Java/SHAFT: TestNG groups and a `<test>` block in `testng.xml` / `testng-{{MODULE_SLUG}}.xml` | A `Workflow` or `Service` class orchestrating page calls (§8.11) |
| A reporting and execution-selection unit Stage `5A` can run by name | A reason to relocate a Test Class out of its §8.4 application/module package |

**Test Classes stay organized by application area and module** (§8.4) — `src/test/java/AdminPages/Admin/Agency/` — while the *suite* that groups them is organized by workflow. Both are true at once because they answer different questions: the directory answers "what does this test," the suite answers "which tests run together."

Each suite records the following. For a Java/SHAFT UI package, each maps to a §8 responsibility area — a suite never creates a home of its own:

| Suite element | Where it actually lives (Java/SHAFT UI) |
|---|---|
| Shared Setup | A Fixture in `src/test/java/utilities/` (§8.5) |
| Shared Teardown | The same Fixture's cleanup (§8.5) |
| Shared Fixtures | `src/test/java/utilities/` (§8.5) — one cohesive fixture per module, preferred |
| Shared Utilities | `src/main/java/utilities/` for technical utilities (§8.9); `src/main/java/Generic_Classes/` for project-wide single-responsibility classes (§8.8) |
| Shared Test Data | JSON under `src/test/resources/{module}/` (§8.6) |
| Shared Components | **Not a default layer** (§8.11). Recorded as `None — §8.11` unless a Component Object is justified against §8.11's three conditions and named in the Automation Plan's Optional Abstractions field. |

The resulting suite structure is recorded in the Automation Plan (§5, "Planned Automation Suites") and, after generation, in the Automation Suite Manifest (§16).

# 11. Automation Knowledge Base

**Distinct from the shared Repair Knowledge Base (`.claude/skills/self-healing-skill/SKILL.md` §10)** — that one stores execution-confirmed *repair patterns*, per the two-layer Knowledge Architecture (`workflows_and_pipelines/pipeline/pipeline.md` §10): recorded by Stage `5H` in the healed module's Repair Summary, and generalized into `platform_core/knowledge/patterns/repair_patterns/`/`platform_core/knowledge/patterns/reasoning/` only via explicit Promotion (§10.5); this section is about reusable *code assets* within one project's own package. Before writing any new automation, also consult both Repair Knowledge Base layers — Platform first, then this project's own — for rules relevant to the flows being automated (e.g., a Login suite checks for any rule tagged "Authentication flows") and apply a matching rule's approach proactively — this closes the loop so a pattern the platform already learned the hard way, via a prior execution's repair, doesn't have to be rediscovered by failing again first.

This skill treats the existing automation project (§9) as a reusable knowledge base, not merely a folder to avoid clobbering. Before creating anything new, it searches for reusable:

- Page Objects / Page Classes (§8.2)
- **Locator Classes and individual locator definitions** (§8.3) — a locator that already has an authoritative definition is reused, never redefined
- Utilities (§8.9) and Generic Classes (§8.8)
- Fixtures (§8.5)
- Helpers already present in the existing project
- Test Data (§8.6)
- **Driver Factory** (§8.7) — always reused, never competed with
- Reusable actions covering a common flow (e.g. login) — reused as the Page or Fixture method they already are, **not lifted into a new workflow or service class** (§8.11)

**Never generate a duplicate reusable asset.** If a page object, utility, or fixture already exists that covers (or can be reasonably extended to cover) a new need, this skill reuses or extends it — it does not author a second, parallel version. Where reuse requires extending an existing asset, that extension is itself planned and recorded (Automation Plan §5, Automation Decision Report §13) rather than performed as an undocumented side effect.

# 11A. Live Selector & DOM Verification (mandatory, headless)

**Every locator this stage emits is confirmed against the running application before it is written into a script.** This is the reasoning grounding that replaces the execution-confirmed evidence the removed Automation Candidate Package used to supply (`pipeline.md` §3.3) — and it is stronger evidence, because it verifies against *the build the suite will actually run on* rather than against a human's earlier pass on a possibly different build.

## 11A.1 Why here, and not in Discovery

Discovery (Stage 2) deliberately captures **no** selectors or DOM structure (`pipeline.md` §3.5). Three reasons, and they matter to how this section is implemented:

1. **Staleness.** A selector captured at Discovery time and used at generation time is verified against an older build. Verifying here reduces that window to zero.
2. **Performance.** Discovery is the platform's broadest sweep; persisting DOM for every screen it visits inflates its runtime and artifacts for data most runs never use.
3. **Clean artifacts.** Discovery's reader is a QA lead reviewing findings, not a consumer of DOM dumps.

The consequence for this stage is explicit: **it must not expect selector data to arrive from upstream.** It acquires that data itself, here.

## 11A.2 Headless, through the Playwright MCP server

Verification runs **headless** by recommendation — the Automation branch's posture throughout (`pipeline.md` §3.4), in deliberate contrast to Stage `4M`'s headed execution. Headless is the right recommendation here because nothing about verification requires human observation: the output is a machine-checkable fact (did this locator resolve to exactly one element?), captured as evidence.

**The mode is still confirmed with the human before live verification starts** *(revised 2026-10-08, `pipeline.md` §6 Rule 11 — live verification is a run against a live application)*. Ask Headed or Headless once, immediately before this stage's first live verification session, recommending Headless and saying why; wait for the explicit answer; record it in the Automation Plan. A configured default is a proposal, never the answer. If the chosen mode cannot be provided (the `playwright` MCP server is registered with `--headless` and has not been restarted without it), stop, say so, and ask again — never switch modes silently. Wherever this section or Execution Rule 11a says "headless", read it as "in the confirmed mode, headless recommended".

A credential value is **never** typed into an MCP tool call (`platform_core/tools/mcp/README.md` §1.3) — authenticate through the platform's credential contract, then verify against that authenticated session.

## 11A.3 What is verified, per test case

For every test case in scope, before its script is emitted:

| Check | Passes when | On failure |
|---|---|---|
| **Reachability** | Every screen the test case's Steps traverse is actually reachable in the target environment, in the stated order | The test case is `Partially Automatable` or `Manual Only` (§13) with the unreachable step named — never emitted as though it works |
| **Locator resolution** | Each interacted element resolves to **exactly one** element under the chosen strategy | Try the next strategy in the §24.1 priority order; if all fail, record `Unverified` (§11A.5) |
| **Uniqueness** | No locator matches multiple elements | Narrow the strategy, or scope it to a container; a multi-match locator is never emitted, since which element it hits is then arbitrary |
| **Interactability** | The element is visible and enabled at the point the Step acts on it | Record the precondition/wait actually required, and generate that wait — this is the single most common source of the flakiness Stage `5H` would otherwise have to repair |
| **Assertable state** | The state the Expected Result describes is observable through some assertable property | The test case is `Partially Automatable` with the unassertable part named — never a weakened assertion to make it fit (§14.1) |

## 11A.4 Verification produces a record, not just a locator

Each verified locator yields a row in the **Selector Verification Report** (§19), and a durable entry in the shared **Selector Verification KB** (`pipeline.md` §10.8 — this stage is its sole writer):

```
Screen/Component:   {name}
Element:            {logical name used in the Page Object}
Strategy:           {role | label | test-id | text | css | xpath}  (§24.1 order)
Locator:            {the actual locator emitted}
Resolved:           {unique | multiple | none}
Interactable:       {yes | required wait: <condition>}
Fallback chain:     {ordered alternates recorded for recovery}
Verified At:        {timestamp}
Code-State Anchor:  {targetRef — what build this was verified against}
Evidence:           {snapshot/screenshot reference}
```

**The code-state anchor is what makes reuse safe later.** A future run reads this record and compares its anchor against current drift (`run_manager.md` §5.8): unchanged means reuse without re-verifying; `moved` or any `unknown-*` means re-verify before trusting (`pipeline.md` §10.8 rule 3).

## 11A.5 Unverifiable is disclosed, never guessed

**A locator that could not be verified is never emitted as though it were confirmed.** Three honest outcomes, in preference order:

1. **Verified** — resolved uniquely and interactable. Emitted, with its record.
2. **Verified with required wait** — resolved, but only after a named condition. Emitted *with that wait generated*, and the condition recorded.
3. **Unverified** — could not be resolved or reached. The test case is downgraded to `Partially Automatable` / `Manual Only` (§13) with the specific element named, and the reason recorded in the Automation Coverage Report as a named gap (§25).

**Never a fourth option.** Emitting a plausible-looking unverified selector converts a generation-time problem this stage could disclose into an execution-time failure Stage `5A` reports and Stage `5H` spends a human approval repairing. A suite that is 80% verified and honest about the other 20% is worth more than one that is 100% emitted and silently 20% broken.

## 11A.6 Time and iteration budget

Verification is bounded, and its bounds are recorded (the same discipline §15A applies to self-review):

- **Per-locator strategy attempts:** capped at the §24.1 priority order — each strategy is tried once, in order, not re-attempted speculatively.
- **Per-test-case verification budget:** a stated time cap. On exhaustion, the remaining elements are `Unverified` (§11A.5) rather than the stage running indefinitely.
- **Reuse before re-verification:** a KB record whose anchor shows no drift is *reused*, not re-verified — this is the main lever that keeps verification affordable on a large suite across runs.
- **Whatever the budget did not reach is stated explicitly** in the Selector Verification Report. Silent truncation would read as "everything verified," which is the one thing this section exists to prevent.

# 11B. Mandatory Knowledge-Base Consultation (before generation)

**Both shared knowledge bases are read before the first line of code is generated, not after a failure** (`pipeline.md` §10.8). Consulting them afterwards is what the platform used to do implicitly, and it meant every known failure mode had to be rediscovered by failing in Stage `5A` and repaired in Stage `5H` — spending an execution cycle and a human approval to relearn something the platform already knew.

## 11B.1 Selector Verification KB — reuse what is already confirmed

For every screen/component in scope, before verifying it live (§11A):

1. Look for an existing verified record.
2. **No drift** (`run_manager.md` §5.8 reports `unchanged`) → reuse the locator and its fallback chain directly; note the reuse and its source anchor.
3. **Drift, or any `unknown-*`** → re-verify live (§11A). The record becomes a *candidate* to try first, never a fact to trust.
4. **No record** → verify live and write the new record.

## 11B.2 Repair KB — pre-empt known failure modes

For every flow in scope, consult confirmed repair/diagnosis patterns and prior runs' Repair Summaries, then **apply matching patterns proactively in the first draft**:

| A KB pattern says | The first draft therefore |
|---|---|
| This app's login redirect races the dashboard assertion (`REPAIR-003`) | Generates the correct wait-for-state up front, rather than a bare navigation assertion |
| This framework's grid rows are index-unstable | Scopes row locators by content, never by index |
| This screen's save is async with no spinner | Waits on the resulting state change, not on a fixed delay |

**Every proactively-applied pattern is cited** in the Automation Manifest, by Rule ID — so a reviewer can see the suite was built on accumulated knowledge, and a later reader can tell an applied pattern from an original decision.

## 11B.3 A KB is evidence, never authority

Neither KB ever tells this stage **what the application should do** — that remains exclusively the approved Project Context's role (`pipeline.md` §6 Rule 5). A KB entry that appears to contradict the approved test case is disclosed as a discrepancy, never silently followed.

# 11C. Brownfield / Greenfield Fit — detect automatically, approve the write

Per the resolved design: **detection is automatic and asks nothing; the write decision is approved explicitly, once, at the existing Automation Approval gate** (`pipeline.md` §5.2). This replaces asking separately about framework, directory, extend-vs-new, and conventions — the over-asking `pipeline.md` §5.5 was written to stop.

## 11C.1 Detected automatically — no prompt

All of this is an Engineering Decision (`pipeline.md` §5.5) and is determined without interrupting:

| Detected | How | Used for |
|---|---|---|
| Ecosystem, framework, pinned versions | `detectStack` (§34.2) | Generating against the real API surface |
| Test directory layout and naming | `detectTestDirs` (`pipeline.md` §13.2) | Placing files where the team already puts them |
| Page-object / fixture / helper patterns | Reading existing test code for **structure and style only** (`pipeline.md` §13.2) | Generating code indistinguishable in style from the team's own |
| Build/test invocation | `package.json#scripts`, Maven/Gradle tasks | Telling Stage `5A` how the team actually runs the suite |
| **Brownfield vs. greenfield** | Existing automation present in `target.automationRoot`? | Choosing between extend and scaffold |

**Reading existing test code is for structure and style, never intent** (`pipeline.md` §6 Rule 9). An existing test's assertions are evidence of what the code currently does — never of what it should do. A conflict with the approved Project Context is a **Finding to report**, never a requirement to adopt.

## 11C.2 Brownfield — extend the team's real suite

Where automation already exists:

- **Extend and reuse rather than duplicate** — a helper, fixture, or page object that already exists is used, not re-created alongside a near-identical twin.
- **Match the existing conventions** even where platform defaults differ. The team's suite is the authority on its own style; a stylistic "improvement" that makes generated files look foreign is a defect, not an upgrade. **Style is not the same as responsibility.** Existing naming, formatting, and layout conventions are matched (§8.13); the §8.10 dependency prohibitions and §15.1 blocking checks still apply to every file this run generates or modifies, and an existing violation is a reported deviation rather than a convention the new code adopts.
- **Report every architecture deviation; refactor nothing silently** (§8.13). Deviations go in the Automation Plan's Architecture Deviations field and, where a correction is proposed, in the Target Write Plan as an individually-approved `MOVE`/`MODIFY` row. A large structural refactor is never performed as a side effect of adding coverage.
- **Never add new complexity because similar complexity already exists.** An existing mixed-responsibility helper does not license a second one (§8.8, §8.11).
- **Never modify an existing file without naming it in the Write Plan** and having it individually approved (§11C.4, `pipeline.md` §13.3). Creating new files in an allowlisted directory is covered by the gate's blanket approval; editing files the team owns is not.
- **Bootstrap Migration** lifts a pre-existing suite into a Workspace Automation Baseline the first time (`pipeline.md` §13.8), so "extend the existing suite" means the team's real suite rather than an empty baseline.

## 11C.3 Greenfield — test infrastructure only

Where no automation exists, scaffold **test infrastructure only** (`pipeline.md` §13.6): the test directory, the framework's config file, the suite itself, and — with approval — the test-script wiring.

**Never scaffold the application:** no source files, no build config, no framework skeleton, no dependency beyond a test-scoped devDependency the human approved. A greenfield run produces a repository ready to *receive* tests, and nothing else.

## 11C.4 The Target Write Plan — the one thing that is asked

Presented at the Automation Approval gate (`pipeline.md` §5.2), as part of the same single approval that covers the suite:

```
Target Write Plan — {Framework}
Fit: {Brownfield: extending existing suite | Greenfield: scaffolding test infrastructure}
Destination: <targetRoot>/<automationRoot>          both resolved, never assumed (§11C.1)
Layout/naming: matched from <detectedTestDirs>      the team's own conventions, not platform defaults

  CREATE  <specDir>/<module>-create.<ext>             [Test]     covers TC-AGENCY-CREATE-001..006
  CREATE  <pageObjectDir>/<Module>FormPage.<ext>      [Page]     new page class
  CREATE  <pageObjectDir>/<Module>Form_Locators.<ext> [Locator]  verified locators (§11A)
  REUSE   <pageObjectDir>/LoginPage.<ext>             [Page]     existing — unchanged, not duplicated
  REUSE   <driverFactoryDir>/                         [Driver]   existing factory reused (§8.7)
  CREATE  <testDataDir>/<module>/create-<module>.json [Data]     externalized test data (§8.6)
  MODIFY  <buildManifest>                             [Config]   + one test-script entry (additive only)

Responsibility areas used: Page · Locator · Test · Fixture · Driver · Utility · Data · Config
Optional abstractions:     None  (or: each one named, with its §8.11 justification)
Architecture deviations:   0     (or: each one named, with its §8.13 classification)
Architecture Review:       Passed | Blocked — {n} unapproved violations (§15.1)

Selector verification: 38 verified · 3 reused from KB (no drift) · 2 unverified (named below)
Self-review: 3 iterations, budget not exhausted, 0 checks left unsatisfied

Every <placeholder> above is RESOLVED per project — from platform.config.json and detectTestDirs
(§11C.1). A plan that names a fixed layout has assumed what it was supposed to detect.
```

Rules, all inherited from `pipeline.md` §13.3 rather than invented here:

0. **Every row states its responsibility area** (§8.1) — a write whose area cannot be stated is a plan defect. For a Java/SHAFT UI package the area also implies the path: a `[Test]` row under `src/main` or a `[Page]`/`[Locator]` row under `src/test` is a §15.1 blocking violation the plan must not carry to the gate.
1. **No Target Project file is written before this plan clears the gate.**
2. **Writes are fail-closed** — absent or empty `target.writeAllowlist` means nothing is written to the Target Project, and generation stays inside `platform_core_data/`.
3. **Every existing file to be modified is named individually** and approved individually.
4. **No deletions**, except a file this platform itself created in a prior run and recorded in the Target Write Ledger.
5. **Filesystem writes only** — the platform never runs `git add`/`commit`/`mv`/`rm` against the Target Project. Generated code is left in the working tree for the team to review and commit with their own conventions and hooks.
6. **Every write is recorded in the Target Write Ledger** — path, run folder, operation, sha256 — the platform's record of what it owns inside someone else's repository.

# 11D. Where this stage generates — resolve it, never assume it

**Step zero of every Stage `4A` pass, before any generation:**

```
node platform_core/tools/automation_lifecycle/cli.js resolve-root --module {{MODULE_SLUG}}
```

| Resolved mode | Where this stage generates | Governed by |
|---|---|---|
| `module` (module is Draft) | `platform_core_data/modules/{{MODULE_SLUG}}/automation/tests_{{FRAMEWORK}}/` | §11D.1–§11D.3 below, unchanged |
| `baseline` (module is Promoted) | `platform_core_data/automation_baseline/{{FRAMEWORK_LOWER}}/tests_{{FRAMEWORK}}/`, **only inside this module's owned paths** | §11D.4 and `pipeline.md` §12.9 |

**For a Draft module this stage generates into the module project and nowhere else** — not into the Workspace Automation Baseline (which only the Workspace Merge writes), not into a temporary run folder (that location is removed), and not directly into the Target Project (that is a projection of an approved baseline, §11C.4).

**For a Promoted module the module project does not exist and must not be recreated.** If the resolver throws `MODULE_DIR_RESURRECTED`, a directory has come back that this lifecycle retired: stop, report it, and do not generate anywhere until it is resolved.

## 11D.1 Standalone is a requirement, not a description

**The module project must be independently runnable — its own config, its own dependency manifest — before it is approved.** Three concrete reasons, each of which fails if it is not:

| Requirement | Why standalone is necessary |
|---|---|
| Stage `5A` executes one module | In a greenfield build the other modules' suites may not be written yet. A project that only runs as part of a whole cannot be executed at all until the whole exists. |
| Stage `5H` heals one module in isolation | A repair's effect must be observable without whole-suite noise. Re-running 400 tests to see whether 3 repairs landed obscures the answer. |
| A reviewer runs it before approving | An Automation Approval gate (`pipeline.md` §5.2) on code the reviewer cannot execute is a formality, not a review. |

Concretely, the project ships whatever its framework needs to run alone — `playwright.config.*` / `pom.xml` / `testng.xml` / `package.json` or equivalent, a documented invocation command, and its own test data. **Standalone-ness is asserted in the Automation Suite Manifest** (`Runs standalone: Yes/No + why`), and a `No` blocks the gate rather than passing with a caveat.

The framework itself is **not** re-selected here: it is bound by `knowledge_base/automation_framework.md`, and this stage complies (§31).

## 11D.2 Shared assets — generated once, proposed never edited

Standalone must not mean duplicated. Genuinely shared assets — base page objects, auth fixtures, common utilities, test-data factories — are generated **once**, into:

```
platform_core_data/automation_baseline/{{FRAMEWORK_LOWER}}/shared/
```

and referenced from each module project by a relative path recorded in that project's config. **This is the one direction in which a module project reads outside itself, and it is deliberate:** duplicating an auth fixture five ways guarantees five drifts.

**A module project never edits a shared asset directly.** When it needs a change there:

1. Record the proposed change in `AutomationDecisionReport.md` — what, why, and which modules it affects.
2. Generate against the asset **as it currently is**, so the module project stays runnable.
3. The change is applied to `shared/` **at assembly time** (`pipeline.md` §12.4 step 6), where it clears the whole-project gate.

The reason is scope, not ceremony: a shared asset is whole-project surface. One module's reviewer approving a change to it would be approving on behalf of every other module's suite.

Record the `shared/` folder's path-scoped commit as `baselineRef` in `.module_automation_state.json` at generation time — that anchor is what the assembly merge's conflict check compares against later.

## 11D.3 Reuse the project in place; never recreate it

A second Stage `4A` pass on the same module **extends the project that already exists**. This is `pipeline.md` §7's in-place-edit discipline applied to code, with git as the version history:

- **Never create a parallel copy** — no `tests_PW_v2/`, no `tests_PW_new/`. Two projects claiming to be one module's suite leaves nothing able to say which Stage `5A` should run.
- **Never delete a test to make room for a regenerated one.** A test case whose script is being replaced has its replacement written over the same file, and the change is recorded in the Automation Manifest.
- **A test that is no longer in scope is not silently dropped.** Report it — a script for a retired test case is a decision for the reviewer, not a cleanup this stage performs unasked.

## 11D.4 Lifecycle state — `.module_automation_state.json`

Written in the module's `automation/` folder, tracking exactly five states (`pipeline.md` §12.3.1):

| State | Set by | Meaning |
|---|---|---|
| `Generated` | **this stage** | Written; not yet executed |
| `Executed` | Stage `5A` | Run; results referenced here by run folder |
| `Healed` | Stage `5H` | Approved repairs applied and the affected tests re-run |
| `Approved` | the §5.2 gate, recorded by the Module Manager | Eligible for assembly into the baseline |
| `Promoted` | `automation_lifecycle/cli.js retire-module` | Assembled, verified, live-proven, working copy retired. **Terminal** — the baseline is now this module's single source of truth |

This stage sets **`Generated` only**. It never writes `Approved` — a stage that could record its own approval would make the gate advisory. It also never advances `Executed` or `Healed`, which belong to the stages that actually did those things, and it can never write `Promoted`, which `setAutomationState` refuses outright.

**Read `sourceOfTruth` before writing anything.** It is `module` or `baseline`, and it is the field the resolver uses. A module in state `Approved` with `sourceOfTruth: baseline` is promoted; the state name alone is never the answer.

## 11D.4a Generating for a Promoted module

Everything in §11D.1–§11D.3 still applies in spirit — standalone-ness, no parallel copies, no silent deletions — with these differences, which follow from the code now living in a tree shared with other modules:

| §11D rule | How it applies after promotion |
|---|---|
| Standalone (§11D.1) | Now a property of the **baseline**, not of a per-module project. It already carries its own `pom.xml`/config and runs on its own; this stage must not break that. The Suite Manifest's `Runs standalone` assertion is made about the baseline. |
| Shared assets (§11D.2) | **Unchanged in rule, simpler in mechanism.** Shared code sits in the same tree now, so "propose, never edit" is enforced by the `shared` classification in `.baseline_ownership.json`: the edit is allowed but must be declared in the Decision Report, because it clears the whole-project gate rather than this module's. |
| Reuse in place (§11D.3) | **Stronger, not weaker.** There is exactly one copy of this module's code in existence. No `tests_v2/`, no scratch copy under the module, no "regenerate then merge". |
| Ownership | **New.** Every path written is classified `owned` / `shared` / `foreign` / `unowned`. `foreign` is a hard stop — never overwrite another module's code. Verify with `cli.js check-ownership --module {{MODULE_SLUG}}` before proposing the change. |
| Module-scoped suite | **New.** Keep `testng-{{MODULE_SLUG}}.xml` (or the framework's equivalent) in step with the classes this module owns, so Stage `5A` and `5H` can still run this module alone. |

## 11D.5 Assembly is the merge's job, not this stage's

On approval, the project is assembled into the whole-project baseline by the **unchanged** three-way merge (`pipeline.md` §12.4) — same hard pre-check, same base/theirs/ours classification, same lock guard, same untracked-file classification, same Merge Summary. Only the merge's *source* changed, from a run working copy to this module project.

- **Greenfield:** every approved module project assembles into `automation_baseline/{framework}/tests_{Framework}/`, which is the deliverable, and is then projected into the Target Project per §11C.4.
- **Brownfield:** the project is generated to match the **detected** layout from the start (§11C.1–§11C.2), so assembly is a merge into the team's existing structure rather than an imposition of the platform's own.

**Ordering is fixed and this stage never shortcuts it:** generate → approve *this module* → assemble into the baseline → then project into the Target Project (`pipeline.md` §13.7). Writing to the Target Project before the baseline is updated would leave the baseline unable to reproduce what the team is looking at.

**After the first assembly comes promotion, and it ends this section's applicability for that module.** Once the merged copy is verified byte-identical and proven by a passing live run, the module project is retired and the module becomes `Promoted` (`pipeline.md` §12.5.1). From then on there is **no assembly step at all** for that module: its next change is written straight into the baseline (§11D.4a) and recorded as an in-place update, because a merge needs two copies and only one exists.

# 12. Traceability


The Automation skill maintains the pipeline's full traceability chain, extended one level further than the Test Design skill's own four-dimension model:

```
Requirement
  ↓
Discovery
  ↓
Finding
  ↓
Evidence
  ↓
Manual Test Case
  ↓
Automation Script
```

Concretely: every Automation Script cites the Test Case ID it automates (1:1). Through that Test Case ID, it inherits — and must not re-derive or alter — the Requirement Reference, Discovery Reference, Finding Reference, and Evidence Reference already established on that test case by the Test Design skill (`.claude/skills/test-design-skill/SKILL.md` §5). This skill's job is to carry that chain forward into the generated code (e.g., as a header comment or metadata block on the script) and into the Automation Decision Report (§13) — never to re-investigate or reinterpret what those references mean.

A gap anywhere in this chain (an Automation Script that cannot cite its Test Case ID, or a Test Case ID that cannot be found in the Traceability Matrix) is itself a defect and must be reported, not silently generated around.

# 13. Automation Decision Engine

**Every test case in the run's scope must receive exactly one automation decision.** No in-scope test case is left undecided. Scope is the approved Stage 3 Manual Test Suite narrowed only by the run's Run Scope / module filter (§23) or an explicit run-scoped instruction (§35) — never by a manual execution outcome (`pipeline.md` §3.3).

**Live verification (§11A) is what most often drives a decision away from "Generate New Automation":** a flow whose screen is unreachable, whose control cannot be uniquely located, or whose Expected Result has no assertable property becomes `Partially Automatable` or `Manual Only` **with the specific element named** — never an emitted script built on an unverified guess.

Possible decisions:

| Decision | Meaning |
|---|---|
| **Reuse Existing Automation** | An existing automation asset (script, page object composition) already covers this test case, as-is or via straightforward composition — no new code is generated for it, beyond wiring it into the appropriate suite. |
| **Generate New Automation** | No suitable existing automation covers this test case; new code is authored, following §14's code-generation standards and, where a Finding Reference is populated, §12's traceability inheritance. |
| **Partially Automatable** | Part of the test case's steps/assertions can be automated reliably; the remainder cannot (e.g., a visual-judgment assertion, a step requiring a manual/offline confirmation). The automatable portion is generated; the non-automatable remainder is explicitly called out, not silently dropped. |
| **Manual Only** | The test case cannot be automated at all with acceptable reliability or safety (e.g., it depends entirely on subjective visual judgment, or it is still an assumption-based test pending verification, or its expected behavior is underspecified in a way that would require inventing business logic to codify). No code is generated for it. |

Each decision must include:

- **Decision** — exactly one of the four above
- **Justification** — why this decision was reached, referencing the specific test case content, existing assets, or specification gap involved
- **Reused Assets** — which existing assets (if any) this decision relies on
- **Generated Assets** — which new assets (if any) this decision produces
- **Automation Readiness** — whether the resulting automation (full or partial) is ready to hand to the Automation Execution skill, or blocked pending something else (e.g., a missing test data fixture)
- **Known Limitations** — anything a future reader should know about this specific automation's reliability, scope, or edge cases it does not cover

This per-test-case record is what becomes the Automation Decision Report (§16).

# 14. Code Generation Standards

This skill generates only maintainable automation. Generated code must be:

- **Modular** — organized into composable units (page objects, fixtures, utilities), not monolithic scripts
- **DRY** — no duplicated logic where a shared utility or fixture already exists or should be created
- **Readable** — clear naming, consistent formatting, and structure a new team member could follow without this skill's own reasoning attached
- **Reusable** — authored so a later suite or test case can compose with it, not so narrowly written that it can only ever serve the one test case that first needed it
- **Maintainable** — resilient to minor UI/application changes (e.g., accessibility-based selectors — roles, labels, text — in preference to brittle CSS/XPath, per v1's carried-forward rule)
- **Versionable** — plain-text, diff-friendly source files suitable for version control, with no generated binary artifacts checked in where a text representation would do

**Prefer composition over duplication** — when a new test case's needs overlap substantially with an existing asset, compose around/extend that asset rather than copying its logic into a new one (§11).

**"Modular" means the responsibilities in §8, not more layers.** For Java/SHAFT UI automation, §8.1's structure and §8.10's dependency direction are the concrete form of every standard above, and §8.11 bounds them: a new abstraction that satisfies "modular" while failing §8.11's three conditions is a defect, not a modularization. Where §14/§14.1 and §8 could be read as differing, §8 governs.

## 14.1 Additional Named Standards

The general standards above (Modular/DRY/Readable/Reusable/Maintainable/Versionable) are made concrete through the following, applied at generation time — not only checked retroactively in Self Review (§15):

| Standard | What it requires |
|---|---|
| **Page Object Model** | Screens are represented as Page Objects — one per page or screen. **For Java/SHAFT UI, this is §8.2's Page Class plus its dedicated §8.3 Locator Class, and locator definitions never live in the Page Class itself.** A **Component Object package is not a default layer** (§8.11): an element reused across pages is represented in each page's own Locator Class, and is factored out only when §8.11's three conditions are met and the abstraction is justified in the Automation Plan. |
| **Reusable Actions** | A multi-step user action performed by more than one test case (e.g., "log in") is a named, reusable method — never re-authored inline per test. It lives with the responsibility that owns it: a single-page action on that page's Page Class (§8.2); test setup or cleanup in a Fixture (§8.5). **It never becomes a workflow or service class merely because it spans two pages** (§8.4, §8.11). |
| **Assertions stay in the test** | A Test Class asserts; a Page Class reports state (§8.2). A verification shared by many test cases is satisfied by asserting on a Page Class's state-reading method, **not** by generating an assertion class or an `assertX()` method on the page (§8.11). Simple, test-specific assertions stay inline in the Test Class. A Validation Rule a suite defines once and many cases cite (`VR-n`, test-design-skill §6.1b) is such a shared verification: read its state once, and keep each case's assertions in the Test Class, one per Assertion ID. |
| **Test Data Separation** | Test data is externalized, never hardcoded inline in a test body — or in a Page Class, Locator Class, Fixture, utility, or base class. **For Java/SHAFT UI it is JSON under `src/test/resources/`, read with the smallest existing mechanism** (§8.6). Technical constants, configuration keys, and framework enums are not test data and may stay in code. Credentials, secrets, and tokens are never in committed test data. |
| **Configuration Management** | Environment-specific values (URLs, timeouts, feature-flag states) live in configuration files/environment variables, never hardcoded into test logic. |
| **Environment Awareness** | Generated automation reads its target environment from configuration (per Configuration Management above) rather than assuming a single hardcoded environment — the same suite must be able to target a different environment by configuration change alone, not a code edit. |
| **Parameterization** | Where a test case's Test Data (§6 of `.claude/skills/test-design-skill/SKILL.md`) implies data-driven variants (e.g., multiple boundary values), this skill generates a parameterized test rather than one copy-pasted test per data value. |
| **Naming Conventions** | Files, test names, and reusable assets follow one consistent convention throughout the generated project — matching the existing convention detected in §9 if an existing project is present, or a clearly stated new convention if greenfield. For Java/SHAFT UI, the locator prefixes in §8.3 apply wherever they do not conflict with an approved existing convention. This is a generation-time standard here; §15's naming-consistency check verifies it was actually followed. |
| **Architecture placement** | **For Java/SHAFT UI automation, every generated file lands in the responsibility area §8.1 assigns it, and the §8.10 dependency direction is respected.** Placement is a generation-time standard, not something corrected retroactively in Self Review; §15.1's blocking checks verify it was actually followed. |
| **No speculative layers** | No workflow, service, assertion class, Component Object package, data factory, builder, adapter, module-specific `BasePage`, or one-method wrapper is generated as a default (§8.11). Each is allowed only against §8.11's three conditions, and each is justified in the Automation Plan. |

Carried forward from v1, still in force:
- Every automated test maps 1:1 to a Test Case ID (§12), stated in the test name or an adjacent, unambiguous comment/metadata block.
- Every automated test is independent and idempotent — safe to re-run without manual cleanup — or uses explicit setup/teardown (§10's "Shared Setup"/"Shared Teardown") to guarantee that.

# 15. Self Review

**Before completing generation, this skill reviews the automation it just produced.** This is not optional and is not the same step as generation itself — it is a distinct, subsequent pass over the finished output.

This skill validates:

- Naming consistency (across the newly generated code and, where applicable, against existing conventions detected in §9)
- Duplicate code (any logic that should have been a shared utility/fixture but wasn't)
- Broken references (a script citing a Test Case ID, page object, or fixture that doesn't actually exist)
- Missing reusable assets (a need that should have produced a shared asset but instead produced one-off, non-reusable code) — bounded by §8.11: a *missing* abstraction is only a finding where §8.11's three conditions are all met, never because one might be useful later
- Missing page objects (a screen interacted with directly instead of through its Page Class), and, for Java/SHAFT UI, a Page Class with no matching Locator Class (§8.3)
- Missing utilities (repeated inline logic that should have been extracted, subject to §8.9)
- Missing test data (a hardcoded value that should have come from externalized test data — for Java/SHAFT UI, a JSON file under `src/test/resources/`, §8.6)
- **Architecture** — the generated project actually matches the Project Architecture and Design Pattern stated in the Automation Plan (§5); a deviation discovered here is corrected or explicitly justified, never left silently inconsistent with the plan. **For Java/SHAFT UI automation this check is the blocking Architecture Review in §15.1**, not an advisory comparison against the plan.
- **Compilation/syntax readiness** — the generated code is syntactically valid and, where a lint/type-check/compile tool is available (§17), passes it; a failure here is a defect this skill must fix before declaring generation complete, not a note left for the Automation Execution skill to discover.
- **Framework compliance** — the generated code actually follows the selected framework's conventions (e.g., SHAFT Engine's DriverFactory/Page Object Model/TestNG/Allure per §8, not generic unwrapped Selenium) — a compliance gap here is exactly the "specification violation" §8 already names, caught before handoff rather than after.
- **Traceability** — every generated script's Test Case ID, and the Requirement/Discovery/Finding/Evidence References it inherited (§12), are actually present and resolvable — distinct from "broken references" above, which checks internal code references (page objects/fixtures); this checks the external traceability chain specifically.
- **Simple English wording** — every user-facing artifact this skill produces (Automation Decision Report, Coverage Report, Automation Summary, Self Review Report) uses short, direct sentences, replaces a hard word with an easier one wherever meaning stays the same, briefly explains any necessary technical term, and keeps a verified fact (e.g. a confirmed selector) visibly separate from a recommendation or limitation (`pipeline.md` §6 Rule 10). Test Case IDs, class/method/file names, and framework terms are never altered by this check.

**This skill generates recommendations whenever improvements are identified** — it does not silently fix everything it finds without recording what it found and why, and it does not silently ship known rough edges without disclosing them. Self Review findings are recorded in the Automation Manifest (§16) and, per iteration, in the Self Review Report (§15A).

|---|---|

| Expected responsibility / location | Where §8 says it belongs |

**Architecture Review is never marked `Passed` while an unapproved blocking violation remains.** Three consequences, so none is inferred:

1. A violation this skill corrected within its budget is recorded as `Resolved` and does not block.
2. A violation this skill could not correct is disclosed exactly as §15A.3 requires, and Architecture Review is reported `Blocked` — never `Passed with notes`.
3. A violation a human explicitly approved as an exception (e.g. a preserved brownfield convention, §8.13) is recorded with that approval named, and does not block. An exception nobody approved is not an exception.

**The §15A.4 prohibition binds here.** Architecture Review is never satisfied by deleting a check, weakening an assertion, or relaxing a boundary so a violation stops being reportable.

# 15A. Self-Review Iteration & Time Budget

**Self-review is an iterative loop with an explicit budget, not a single pass and not an open-ended pursuit of perfection.** Reasoning quality improves materially over the first few passes and then flattens; without a stated bound, this stage would either stop arbitrarily after one pass or grind indefinitely against checks that cannot be satisfied in this environment.

## 15A.1 The loop

```
iteration := 1
while iteration <= MAX_ITERATIONS and time_spent < TIME_BUDGET:
    run every §15 check
    if no findings:              -> converged, exit
    if only unfixable findings:  -> exit, disclose them (§15A.3)
    fix what is fixable
    record iteration: findings, fixes, checks still failing
    iteration := iteration + 1
```

## 15A.2 The budget

| Bound | Default | Rationale |
|---|---|---|
| **MAX_ITERATIONS** | **3** | Pass 1 catches structural issues; pass 2 catches what those fixes introduced; pass 3 confirms stability. A 4th pass rarely finds anything a human reviewer would not prefer to judge themselves. |
| **TIME_BUDGET** | Stated per run, scaled to suite size | Prevents a large suite's review from dominating the run. |
| **Convergence** | Exit early on a clean pass | The budget is a ceiling, never a quota — three iterations are not run for their own sake. |
| **Oscillation guard** | Exit on a repeated finding-set | A finding that reappears unchanged after a fix attempt will not be resolved by attempting it again; it is disclosed instead. |

Both bounds, and what was actually consumed, are recorded in the Self Review Report (§19).

## 15A.3 Exhaustion is disclosed, never silent

**When the budget ends with checks unsatisfied, every one is named** in the Self Review Report and surfaced at the Automation Approval gate (`pipeline.md` §5.2, which reviews for exactly this):

```
Self-Review — 3 iterations, budget exhausted
  PASS  traceability · naming · duplication · page objects · framework compliance · compilation
  FAIL  2 checks unsatisfied:
          - TC-AGENCY-014: assertion depends on a value only verifiable via DB access (out of scope)
          - AgencyGridPage: rows index-unstable; content-scoped locator added, still order-sensitive
```

A silently-truncated review reads to a reviewer as a clean one. That is the specific failure this section prevents: an unsatisfied check disclosed is a reviewer's decision to make, while an unsatisfied check hidden is a defect shipped with the reviewer's signature on it.

## 15A.4 What self-review may never do

The §14.1 prohibitions bind here exactly as they bind Stage `5H` (`pipeline.md` §5.6.4): self-review **never weakens an assertion, removes a check, widens an expected value, or adds a tolerance** to make its own generated code pass its own review. A check that cannot be satisfied honestly is disclosed (§15A.3) — never satisfied by lowering the bar.

# 22. Architecture Principle

> Agents communicate through artifacts only. Each has a single responsibility. Every output becomes the input of another whenever applicable.

For this skill specifically: it is responsible for producing a **production-ready automation project**, not merely isolated automation scripts — planning, framework justification, reuse, suite organization, per-test-case decisions, and self review are all part of that responsibility, not optional extras.

**"Single responsibility" is also the architecture rule inside the generated code, not only the rule between stages.** A Test Class tests, a Page Class acts and reports state, a Locator Class defines locators, a Fixture prepares and cleans up, the Driver Factory owns the driver, and test data lives outside the code (§8). A layer that exists to sit between two of those, without meeting §8.11's conditions, adds a responsibility no one asked for — which is the same defect at a smaller scale. **Execution belongs exclusively to the Automation Execution skill.** This skill's outputs — the Automation Package, Plan, Manifest, Decision Report, Coverage Report, Suite Manifest, and Automation Summary — become the Automation Execution skill's sole input in the next stage.

# 24. Locator Strategy

Generated automation must use a deliberate, prioritized approach to identifying elements — never a single brittle strategy applied uniformly.

**Where a locator lives is settled separately from how it is chosen.** §24 governs the *choice* of locator; §8.3 governs its *home*. For a Java/SHAFT UI package every locator this section produces is declared in exactly one Locator Class, and never in a Page Class or a Test Class — whatever priority level it ended up at. A verified locator is never replaced merely for naming or style, and moving one preserves its Selector Verification record (§8.3, §11A.4).

**An approved project locator convention governs the naming, not the priority order.** Where the project's `automation_framework.md` states a convention such as §8.3's `Btn_`/`Txt_` prefixes, that convention applies to the locator's *identifier*; §24.1's priority order still decides *what the locator matches* (§34.5).

## 24.1 Priority Order

1. **Accessibility-based locators** — role, label, accessible name, or visible text (e.g., Playwright's `getByRole`/`getByLabel`/`getByText`, or the equivalent construct in the selected framework). Preferred: resilient to styling/DOM-structure changes, and doubles as an accessibility signal.
2. **Stable data attributes** — a dedicated test-id attribute (e.g., `data-testid`) where the application exposes one. Preferred when accessibility-based locators are ambiguous or unavailable for a given element.
3. **Structural/semantic selectors** — a stable, unique CSS selector based on semantic structure (e.g., a form's labeled input), used only when neither of the above is viable.
4. **XPath/brittle CSS position-based selectors** — last resort only, and always flagged in the Automation Decision Report (§13) or Self Review (§15) as a known fragility risk, never used silently as if it were a first-choice locator.

## 24.2 Fallback and Recovery

- Where the top-priority locator type is not viable for a specific element (e.g., no accessible role/label exists and no test-id is present), this skill falls back down the priority order and **records which level it had to fall back to and why**, in the relevant Automation Decision's Known Limitations field (§13).
- This skill never silently settles for a Level 4 (brittle) locator without recording the recommendation to add a stable `data-testid` or accessible label to that element — this recommendation belongs in the Automation Manifest's Self Review section (§15) or the Automation Decision Report (§13), so a human can act on it even though this skill cannot modify application code itself.
- A locator that cannot be made reliable at any priority level (e.g., a dynamically regenerated, non-deterministic identifier) is a `Partially Automatable` or `Manual Only` signal for that portion of the test case (§13) — this skill does not force a flaky locator into passing automation just to claim full coverage.

# 27. Recovery Strategy — Minimal Prerequisite Recommendation

Like the Test Design skill (`.claude/skills/test-design-skill/SKILL.md` §20), this skill has no alternate generation mechanism to fall back to — its recovery behavior is: **never let one blocked test case stop the whole run, and always name the smallest thing that would unblock it.**

1. When a Local Stop Condition (§26) blocks a specific test case, this skill continues processing every *other*, unblocked test case in the run's scope — a single blocked case is never a reason to produce zero output for the run.
2. For the blocked case, this skill states the **smallest missing prerequisite** that would resolve it — never a vague "cannot automate." Examples: *"Add a `data-testid` to the Airlines multi-select dropdown"*, not *"selectors unreliable"*; *"Confirm the maximum airline-selection count with the DBA (T3087 Prerequisites)"*, not *"requirements incomplete."*
3. For a Global Stop Condition (§26), this skill still states the minimal prerequisite (e.g., *"Awaiting Test Design skill re-run — Coverage Report for RUN-20260710-001 is still Pending Review"*) rather than a bare halt message.
4. The recommended prerequisite is recorded in the Automation Plan's "Blocked Tests" field (§5) and in the Automation Summary's Known Limitations section (§25) — never only in a narrative aside a reviewer could miss.

# 27A. Generation Permission Is Not Execution Permission

*(Added 2026-08-07, user-mandated — Execution Safety.)*

**This skill's eligibility gate is unchanged**, and this section changes nothing about it:

```text
Review = Approved   AND   Automation = Approved      → in scope for Stage 4A
```

What it establishes is what that gate does **not** mean.

```text
TC-X — Delete Agency
Review:      Approved      ← the test case is correct
Automation:  Approved      ← it should be automated
```

This skill may generate the automation for it, if that is valid under §13's decision engine. **It may not thereby authorize the deletion.** Whether the generated code's `DELETE` may ever run against a live environment is a separate question, answered separately, later, by the Execution Safety policy at Stage `5A` (`.claude/skills/automation-execution-skill/SKILL.md` §14A).

**Capability does not imply authorization.** That this skill *can* generate a payment test does not mean Stage `5A` may execute payment on staging.

**Three independent concerns:**

```text
Review            Is the Test Case accepted?
Automation        Should it be automated?              ← this skill's gate
Execution Safety  May this action execute here, now?   ← not this skill's gate, and never becomes it
```

**What this means in practice for this skill:**

- **Do not narrow generation scope by safety.** A case whose operations are currently `Forbidden` on this environment is still a legitimate automation asset — environments change, policies change, and an asset that exists is what makes a future authorized run possible. Excluding it here would silently convert a *this-environment* restriction into a *permanent* coverage gap.
- **Do disclose it.** Where §13's decision is `Generate New Automation` and the case's operations are not currently executable under the policy, say so in **Known Limitations** on that decision (§13) — *"generated; `DELETE` on `Shared` is `Forbidden` on Staging under policy `ndc-admin-portal-stg` v1, so this asset is not currently executable there."* A reviewer reading the Decision Report should never be surprised at Stage `5A`.
- **Never record a safety decision as an automation decision.** `Manual Only` (§13) means *cannot be automated with acceptable reliability*. It does not mean *not currently permitted to run*. Collapsing the two would lose the distinction between "we can't write this" and "we're not allowed to run this yet", and only one of those is ever fixed by writing better code.
- **Live selector verification (§11A) is itself an execution.** It is read-only by construction — it locates elements and does not act on them — and so resolves `Allowed` under any policy whose reads are open. It must stay that way: §11A must never submit a form, approve a record, or click a destructive control to confirm a locator.

# 29. Future Scalability

The abstractions this revision relies on — Framework Detection/Selection (§6–§8) already agnostic about *which* framework, Locator Strategy (§24) already framed as "element identification priority" rather than "CSS selector," and Suite Planning (§10) already organized by business workflow rather than by page — extend to non-web-UI systems with, at most, a new framework entry and a new locator-equivalent concept, never a change to the Traceability Model (§12), Automation Decision Engine (§13), Standard Output Contract (§25), or Handoff Contract (§28):

| Future system shape | How it fits today's model |
|---|---|
| **Web** (current) | Baseline — Playwright/Selenium/Cypress-class frameworks, DOM-based locators. |
| **API** | REST Assured/Postman (already listed, §6) as framework; "locators" become endpoint/field-path identification (request path, JSON field name) — same priority-order concept (stable named field over positional array index), same fallback/recovery recording. |
| **Mobile** | Appium (already listed, §6) as framework; locators become accessibility-ID/label-based (the mobile-equivalent Level 1 in §24.1) over coordinate-based taps (the mobile-equivalent Level 4). |
| **Desktop** | A desktop-automation framework (e.g., WinAppDriver-class tooling) slots into §6's extensible framework list the same way SHAFT/Appium already do. |
| **Microservices** | Suite Planning (§10) groups by business workflow across services, exactly as it already groups UI test cases across pages — a workflow spanning three services is still one suite, not three. |
| **Message Queues** | "Steps" become publish/consume actions; Test Data Separation (§14.1) already covers externalizing message payloads into fixtures. |
| **Batch Jobs** | "Steps" become job-trigger actions; Environment Awareness (§14.1) already covers running the same automation against different job environments via configuration. |
| **Cloud Resources** | Framework Detection (§6) extends to a cloud-provider SDK/CLI as the "framework"; Configuration Management (§14.1) already covers environment-specific credentials/resource identifiers. |

**What would need to change, explicitly, and what would not:** supporting any of the above requires naming the new framework (§6) and its locator-equivalent priority order (§24) for that system shape — it requires **no change** to the Traceability Model (§12), the Automation Decision Engine (§13), the Suite Planning organizing principle (§10), the Standard Output Contract (§25), or the Handoff Contract (§28). Those are already defined in terms of test cases and evidence, not in terms of "a browser."

**§8.1's Maven structure is never carried across a system shape** (§8.12). It governs Java/SHAFT UI automation and nothing else: an API, mobile, messaging, batch, or cloud package uses its own approved structure, and a framework with an explicitly documented project structure keeps it. What travels between shapes is the set of principles, not the folders — readable test flow, interface actions separated from tests, no duplicated element or endpoint definitions, externalized test data, reusable setup and cleanup, and no unnecessary layers. §15.1's blocking checks apply in each shape's own terms wherever that shape's approved architecture states the equivalent boundary; a check that has no meaning for a shape (e.g. "a Page Class without a Locator Class" in a message-queue package) is recorded `Not applicable`, never quietly dropped.

# 30. Automation Start Decision Gate

**This is orchestration-level, not this skill's own internal step — it governs whether/how this skill gets invoked at all.** Full specification lives at `workflows_and_pipelines/pipeline/pipeline.md` §5.4; restated here because it directly bounds this skill's authority.

Whenever a human requests automation (or any single downstream stage) for a project, whoever/whatever is orchestrating the pipeline — a human, a script, or a skill acting in that capacity — must never unilaterally decide whether to: resume from the latest approved stage, run the full pipeline from Stage 1, or skip straight to generating automation. It must first inspect the actual stage state — the artifact headers in the module workspace for Stages 1–3 and `4A`, and the run's Run Manifest for run-level stages — present it (which stages are Approved/Pending/absent), and ask. See `workflows_and_pipelines/pipeline/pipeline.md` §5.4 (Workflow Selection & Start Decision Gate) for the required interaction format and options. This skill must never begin generating an Automation Plan or any code until that upstream decision has been made explicitly by a human — "the user asked for automation" is not, by itself, authorization to also silently run or skip Stages 1–4. A human's **Full Automation** selection under `pipeline.md` §5.4 *is* that explicit decision; it lets the orchestrator invoke this stage once Stage 3 is `Approved` (§5.4.2), and it never answers this skill's own gates (§31–§33) in advance.

# 31. Framework Decision Gate

**Framework selection (§6–§8) is never a decision this skill makes and silently proceeds on — it is always a question put to a human, even when the answer looks obvious.** This section is the mandatory interaction that must complete before any Automation Plan (§5) is written or any code is generated.

## 31.1 Step 1 — Inspect and summarize every existing framework's project (v8: one row per framework, never more)

Before asking anything, this skill reads `AutomationPackages.md` (§19) — the project's registry of every framework this project has an authoritative Automation Package for — and, for each entry, inspects the actual code (§9), not just the registry's own claim about it. **A project may use several different frameworks, but never more than one project per framework.** This skill then summarizes plainly, e.g.:

```
Existing automation projects for NDC:
1. tests_Playwright — Playwright + JavaScript, 3 tests (Login), last touched RUN-20260712-001
2. tests_SHAFT — none yet
```

or, if the registry is empty/absent, "No previous automation projects exist for this project."

## 31.2 Step 2 — Ask, never infer

Per §31.6's Human Decision Principle, gather the options above, analyze them, present a recommendation with justification, and ask the human — never infer:

```
1. Extend the existing project for this framework (if one exists).
2. Start a project for a framework that doesn't have one yet.
3. Reset this framework's project from scratch (rare — discards the current
   baseline entirely; requires explicit confirmation, never a default).
```

- **If starting a project for a framework with none yet:** ask which framework to use. Present at minimum the frameworks the Project Context or run configuration has ever mentioned, plus the standard list (§6) — e.g. "SHAFT / Playwright / Selenium / Cypress / Other" — and let the human pick, or name one outright if the Project Context already states one explicitly (§7 Rule 1) — but *confirm* it via this same question rather than silently assuming the stated framework is still what's wanted (§7 Rule 1's own updated text).
- **"Extend" is the default recommendation whenever a project already exists for the chosen framework** — a second, independent, competing project for the same framework is never an available option; that gap (this platform's own former "v5" behavior) is exactly what produced NDC's `tests_SHAFT`/`tests_SHAFT_Agency` split, later consolidated back into one project (see `AutomationPackages.md` Notes, 2026-07-24).
- **"Reset" is rare and destructive** — it discards the current baseline's content entirely. Never offered as a casual alternative to "Extend"; only surfaced, with its consequence stated plainly, when the human has reason to believe the existing project is genuinely unsalvageable.
- **This skill's own criteria-based analysis (§7) is offered as a labeled recommendation inside this question, never substituted for it.** "Based on X/Y/Z, extending the existing SHAFT project looks correct — proceed with that, or choose differently?" is acceptable framing; silently proceeding with the recommendation is not.
- **This question is asked before every Stage `4A` run**, not only the first one for a project — a prior run's answer is never treated as a standing default for the next run.

## 31.3 Step 3 — Never infer the framework from Discovery tooling

Per §6's hardened language: which tool Stage 2 used for Browser Automation must never appear as a factor in this question or its recommendation. If Discovery used Playwright and the project's actual Automation Framework is SHAFT (or anything else), the question in §31.2 is asked exactly the same way — Discovery's tool choice is invisible to this decision.

## 31.4 Recording the outcome

The human's actual answer — not this skill's recommendation — is what gets recorded in the Automation Plan's Target Framework/Target Language fields (§5), with the recommendation (if one was offered) noted alongside it for traceability. A Framework Decision Gate that was asked but whose answer wasn't recorded verbatim is treated as incomplete, per the same standard as any other missing Automation Plan field (§5). This skill also updates `AutomationPackages.md` (§19) with the outcome — a new framework's project added, the existing one's "last touched" run updated, or (on Reset) the project's history noted as reset — so the next Stage 4A run's Step 1 summary is accurate without re-deriving it from scratch.

## 31.5 Platform Principle (v8)

**Discovery technology != Automation technology, and one authoritative project per framework, project-wide.** Playwright may be the tool that inspected the application in Stage 2, and is also this stage's mandatory selector-verification mechanism (§11A.2) — **neither fact carries any weight in the framework choice.** SHAFT, Playwright, Selenium, or Cypress may each independently have their own one authoritative project for that same platform project. A framework choice made for one Stage `4A` invocation binds that framework's one project for the whole repository, not just that run — extending it is the expected path for every subsequent run targeting the same framework, never a coexisting second package.

## 31.6 Human Decision Principle for Repository-Structure Decisions (added 2026-07-24, user-mandated)

For every decision that affects Automation Project/package selection, framework selection, creation of a new framework's project, merge destination, or repository structure generally, this skill must never decide autonomously. It must:

1. **Gather** the available options (read the registry, inspect the actual code per §9).
2. **Analyze** them against the criteria this specification already names (§7, Existing Framework Analysis).
3. **Present a recommendation with justification** — never a bare option list with no stated reasoning, and never a silent pick.
4. **Wait for explicit human approval** before proceeding. No default or inferred decision is allowed, even when the "obviously correct" answer seems clear from context.

This is not a new category of judgment call — it is the existing discipline §31.2's "ask, never infer" and §5.5 of `workflows_and_pipelines/pipeline/pipeline.md`'s Human Decisions list already require — restated here as its own named principle because it must extend explicitly to merge destination and repository structure, not only to the original Framework/Target/Strategy questions. A concrete case this caught: consolidating two SHAFT packages back into one surfaced that the newer package's test-class redesign silently dropped a business-rule-backed regression assertion the older one had — exactly the kind of thing that must be surfaced and decided by a human, never silently resolved either way by this skill.

# 32. Reference Automation Project

**A project may designate an external, real, human-owned automation codebase as its Reference Automation Project** — e.g. a company's production SHAFT repository living outside this platform's own repository entirely (`E:\...` on local disk, or any path outside `platform_core_data/modules/{{MODULE_SLUG}}/automation/`). This is distinct from the platform's own generated Automation Packages (§19, §31): it is not generated by this skill, is not one of the `tests_{Framework}/` packages in the registry, and is never assumed to be the same thing as "an existing automation package" in the §9/§31.1 sense — it gets its own handling.

## 32.1 Registration

Once a human designates a Reference Automation Project (path + a brief description of what it is), this skill persists it as durable project knowledge — e.g. `platform_core_data/knowledge_base/reference_automation_project.md` — recording: the path, a one-time Architecture Summary (§32.4), and the standing read-only default (§32.2). This registration is a one-time analysis, not repeated every run — subsequent runs read the persisted file rather than re-inspecting the reference project's entire codebase from scratch, unless the human explicitly asks for a re-analysis.

## 32.2 Read-Only by Default

**A registered Reference Automation Project is never modified unless the human explicitly selects "Update the Reference Project directly"** via the Automation Target Decision Gate (§32.3). Default handling is always: inspect, learn from, generate code *compatible with* its architecture — never edit its files in place without that explicit choice, every time it's chosen (a prior run's "yes, update it" is never treated as a standing default for the next run either).

## 32.3 Automation Target Decision Gate

**Distinct from, and asked alongside, the Framework Decision Gate (§31) and the Automation Strategy Decision Gate (§33) — never assumed, never defaulted.** Whenever a project has a registered Reference Automation Project, this skill asks, before generating anything:

```
Automation Target
1. Generate inside the platform (a platform-tracked Automation Package, §19/§31).
2. Export a package compatible with the Reference Project (generated within the platform's
   own workspace, but structured to drop into the Reference Project's conventions with
   minimal rework).
3. Update the Reference Project directly (writes into the Reference Project's own repository —
   requires the read-only default in §32.2 to be explicitly overridden for this run).
4. Write into the Target Project's own test directories ({{TARGET_ROOT}}/<automationRoot>) —
   the installed-platform default. Generates at the module's resolved root (the module
   project while Draft, merged to the baseline on approval; the baseline's owned paths once
   Promoted, recorded after approval), then projects into the Target Project per
   pipeline.md §13.3.
```

**Option 4 is available whenever `platform.config.json` declares `mode: "installed"` with a non-empty `target.writeAllowlist`** (`pipeline.md` §13.3), and in that case it is the **presented default** — the generated suite belongs in the repository the team actually runs their tests from. It is still asked, never assumed (§31.2's "Ask, never infer" is unchanged). Choosing it does not change *where generation happens*: the run's working copy and the Workspace Automation Baseline are unchanged, and the Target Project receives a projection of the baseline only after Automation Approval and the Workspace Merge, in that fixed order (`pipeline.md` §13.7).

If `writeAllowlist` is empty or absent, Option 4 is not offered at all — target writes are fail-closed, and Option 1 is the behavior that applies (`pipeline.md` §13.3).

If no Reference Automation Project is registered for this project, Options 2 and 3 are skipped (there is nothing to target) — with Option 4 available this gate still asks between generating inside the platform and writing into the Target Project; with Option 4 unavailable too, there is no choice left to make and this skill proceeds directly to the Framework Decision Gate (§31) and Automation Strategy Decision Gate (§33) as already specified.

## 32.4 Architecture Summary

The one-time registration analysis (§32.1) must produce and persist a plain-language Architecture Summary covering, at minimum: detected framework + version, language + version, build system, project/module structure, Page Object (or equivalent) pattern, base/shared classes, driver initialization pattern, test data strategy, configuration management, reporting solution, naming conventions, and reusable utilities/helpers/wrappers/assertions this skill should always prefer reusing over authoring new equivalents. Any pre-existing inconsistency, duplication, or drift discovered during this analysis (e.g., a locator that no longer matches the live application, two competing driver-init patterns) is recorded plainly, not silently smoothed over — it is knowledge for a human to act on, not this skill's to fix unilaterally.

## 32.5 Generation Rules When a Reference Project Governs (Target = Export or Update)

- **Never recreate SHAFT (or whichever framework's) infrastructure or framework boilerplate that already exists in the Reference Project** (driver factory, base test classes, reporting wiring) — generate only the business/page-specific automation code that fits its existing architecture.
- **Reuse existing utilities and patterns whenever possible** (per the persisted Architecture Summary, §32.4) rather than authoring parallel equivalents.
- Extend an existing Page Object for a screen already covered there (e.g. a Login page class) rather than authoring a competing one from scratch — this is the Reference Project's own version of §11's Automation Knowledge Base rule.
- **The Reference Project's explicitly documented architecture takes precedence over §8.1's structure** (§8.12) — that is what "generate code compatible with its architecture" means. Two things this precedence does **not** do: it does not suspend the §8.10 dependency prohibitions or the §15.1 blocking checks for newly generated code, and it does not license adding complexity the Reference Project merely happens to contain (§8.13). Where the Reference Project's architecture and §8.1 differ, the difference is recorded in the Automation Plan's Architecture Deviations field so the precedence is visible rather than assumed.

# 33. Automation Strategy Decision Gate

**Distinct from §32.3's Target question and §31's Framework question — all three may be asked together in one exchange, but are conceptually separate answers, none inferred from the others.** Before generating anything, ask:

```
Automation Strategy
1. Extend the existing project for this framework (if one exists).
2. Start a project for a framework that doesn't have one yet.
3. Reset this framework's project from scratch (rare — discards the current
   baseline entirely; requires explicit confirmation, never a default).
```

This is the same question already specified at §31.2 — restated here as its own named gate per explicit user instruction, so it is never accidentally treated as a sub-clause of the Framework question alone. It applies whether the Automation Target (§32.3) is "inside the platform" or "compatible with/updating the Reference Project" — extend vs. start-new-framework vs. reset is a live question in either case. As of v8, this is never framed as "continue vs. a completely new, coexisting package for the same framework" — that option no longer exists (§31.5).

## 33.1 Presentation — one consolidated gate, asked once per stage

**§30/§32.3/§31.2/§33 are presented to the human together, as one Decision Gate, not as separate questions across turns:** (1) proceed with Stage `4A` now; (2) Automation Target (§32.3); (3) Framework (§31.2); (4) Automation Strategy (§33). **The brownfield/greenfield determination is *not* one of these questions** — it is detected automatically (§11C.1), and its consequences are approved later, as the Target Write Plan at the §5.2 gate (§11C.4). Every option is shown at once so the human answers all four in a single exchange, and no sub-question is silently skipped (e.g. never omit Framework just because Target implies an obvious answer — ask it, even if the expected answer is predictable from context). **Once this consolidated gate is answered, this skill does not ask again during that Stage `4A` run** — it proceeds straight through Automation Plan → generation → the full Standard Output Contract (§25) without further confirmation dialogs, reserving any further pause exclusively for a genuine technical blocker encountered during generation (§26 Stop Conditions), never for a repeat or refinement of a decision already made.

# 34. Stack Documentation Step (Context7)

**Mandatory, and it runs at a fixed point:** after the Framework Decision Gate (§31) has resolved the framework and Working Copy Creation (§33.2) has brought in the baseline, and **before any code generation begins** (§14). It informs *how* code is written; it never decides *what* is tested.

Full specification: `platform_core/tools/mcp/README.md` §2. This section states the obligation and the stop conditions; the mechanics live there, once.

## 34.1 Why

Automation written from model memory drifts from the stack it must actually run on — an API removed two minor versions ago, a renamed config key, an assertion helper that never existed at the pinned version. When the authoritative, version-specific documentation is fetchable, guessing at a dependency's surface is a defect, not a shortcut.

## 34.2 Extract the stack from the project — never assume it

The stack is discovered from the project under test and its resolved automation project, in both of the forms the project actually records it:

1. **Source code** — dependency manifests and lockfiles (`package.json`/lockfiles, `pom.xml`, `build.gradle(.kts)`, `requirements.txt`, `pyproject.toml`/`poetry.lock`, `Pipfile.lock`, `*.csproj`, `Gemfile.lock`, `go.mod`, `composer.lock`) plus framework config (`playwright.config.*`, `testng.xml`, `cypress.config.*`, `pytest.ini`, SHAFT's `src/main/resources/properties/`). Run `node platform_core/tools/mcp/stack_docs/cli.js --root <resolved automation project> --json` for this — the shared extractor is the single source of truth for detection, exactly as `run_manager` is for run folder names. Never hand-assemble the dependency list when the tool can produce it.
2. **Documentation** — the project's own stated stack: the approved Project Context's Technology Stack section, `platform_core_data/knowledge_base/architecture.md`, `automation_framework.md`, `run_configuration.md`, `onboarding.md`, and `stack.md` (what a prior run already detected, plus any Human Corrections recorded against it — read this before re-detecting, per §34.4).

**The lockfile wins on version.** A manifest range (`^1.61.1`) is a constraint; the lockfile's resolved version is the fact, and it is the version documented. Where only a range exists, the artifact records it **as a range, flagged unpinned** — never presented as a resolved version.

Where the two sources disagree (documentation says Selenium, the manifests say Playwright), that contradiction is surfaced in the Automation Plan's Assumptions/Risks and at the §31 gate — **never** silently resolved in favor of either. Extracted stack facts do not override the Framework Decision Gate's answer; a manifest containing Playwright is not authorization to generate Playwright.

## 34.3 Query

Per material library (§2.4 of `mcp/README.md` — what the generated code actually imports, not transitive dependencies): `resolve-library-id` with the name **plus the concrete question**, preferring a **version-specific library ID** whenever the version is pinned, then `query-docs` scoped to **one concept per call**. `stack_docs/planQueries.js` produces the concept list and the exact questions; a combined multi-concept query returns shallow results for each and is not how this step is performed.

## 34.4 Output — one per-run artifact, one durable record

**Per run, before generation:** `platform_core_data/modules/{{MODULE_SLUG}}/automation/StackDocumentationContext_{Framework}.md`, containing Detected Stack, Dependency Table (library · resolved version · pinned? · source file · Context7 ID · queried?), Queries Performed, Guidelines Extracted, Conflicts, and Documentation Gaps — per `mcp/README.md` §2.5.

**Durable, shared across runs:** the same detection also updates `platform_core_data/knowledge_base/stack.md` **in place** — Detected At, Ecosystems, Automation Framework, Dependency Table, and Conventions Observed. The split follows the §10.4 rule that a run folder holds what happened *in that run* while `knowledge_base/` holds what is true of the *project*: which Context7 queries this run made is run history, whereas the stack those queries were about outlives the run. A later run reads `stack.md` first and re-detects to confirm rather than starting blind.

Two rules govern writing it:

- **Never silently overwrite a human correction.** `stack.md`'s Human Corrections section is authored by people. Where detection contradicts an entry there, the conflict is surfaced in the Automation Plan's Assumptions/Risks and at the §31 gate — the detected value does not replace the correction.
- **Never write business logic, requirements, or application behavior into it.** It records the *toolchain*, and nothing that belongs in the Project Context or a Finding.

The Automation Plan (§5) cites this artifact and records the version-specific guidelines that shaped generation. **A run against a pinned-version stack with zero queries performed and no recorded documentation gap is an incomplete Automation Plan** — the same standard §7 applies to an unjustified framework choice.

## 34.5 The approved project framework governs

Fetched documentation is a **guideline input, never an authority over approved project standards.** Where Context7's idiomatic layout contradicts `platform_core_data/knowledge_base/automation_framework.md` (e.g. an idiomatic Playwright structure against SHAFT's Pages/Locators/Tests/Data layering, or accessibility-first locators against the `Btn_`/`Txt_` prefix convention), the **approved framework wins**; the conflict goes in the artifact's Conflicts row and the Plan's Assumptions/Risks, resolved by a human exactly as that document's Gap Resolution Rule requires. Fetched docs never license redesigning an approved framework, and never appear as justification for a coverage decision, a Finding, or a test case's existence — they are outside the traceability chain (§12).

## 34.6 Stop conditions

Consistent with §26–§27 (mark the specific gap, continue generating everything else, never a bare halt):

- **`context7` unavailable or unapproved** — record it as a documentation gap in the artifact and proceed, generating from the pinned versions and the existing project's established conventions. Never present model-memory recall as fetched documentation.
- **No credible library match, or no docs for the pinned version** — recorded per-library as a documentation gap, never backfilled from memory and never silently dropped.
- **No material dependency detected at all** — a documentation gap, not an assumed stack. If the framework is resolved but its dependencies are undiscoverable, that is stated plainly in the Plan's Risks.

# 35. Direct Invocation

This skill is independently invocable — `/automation-skill`, optionally with a run-scoped instruction (e.g. `/automation-skill automate the Login candidates only`). Full rules: `workflows_and_pipelines/pipeline/pipeline.md` §5.3.1.

**The §30 Automation Start Decision Gate is unchanged and still fires.** A direct call authorizes *this* skill to begin its own work; it is never authorization to run, resume, or skip Stages 1–4 (§5.3.1 #2, Execution Rule 28). §5.3.1 relaxes only *who may start this stage and when* — not §30's requirement that the upstream-state decision be made explicitly by a human.

- **Instruction prompts are run-scoped, never spec-overriding** (§5.3.1 #3). An instruction may select which candidate test case IDs to automate, prioritize a suite, or set a generation order. It never authorizes selecting a framework unilaterally (§31 — a Human Decision), choosing a merge destination or repository structure (§31.6), writing anywhere other than the module's resolved root and owned paths (Execution Rule 35), reading the PRD (Execution Rule 2), inventing business logic, or executing what it generates (this skill never executes).
- **Upstream `Pending Review` → request approval, then recommend** (§5.3.1 #4). Report which required input is open, then offer both paths (approve → `/automation-skill`, or revise → `/test-design-skill <feedback>`). **Never `/manual-execution-skill`** — that is the other branch and is not upstream of this stage (`pipeline.md` §3.3).
- **Missing upstream → run degraded** (§5.3.1 #5):
  - *No approved Manual Test Suite:* the scope of what to automate is undefined — halt (§26). If the invocation itself names specific test case IDs, treat that named list as the scope and record it in the Automation Plan as `Scope source: direct invocation, no approved Test Suite`, with every generated test marked `Requires Upstream Stage`.
  - *No Selector Verification KB / Repair KB:* proceed — verify everything live (§11A) and state that no prior art was available. This is a normal first run, not a degraded one.
  - *Application unreachable:* halt rather than emit unverified locators (§26).
  - *No Manual Test Suite:* blocking for any candidate whose full content it would supply — report per §26/§27's minimal-prerequisite form.
  - *No Traceability Matrix / Coverage Report:* generate anyway; mark the Automation Plan's traceability section `Requires Upstream Stage`.
- **Closing message must recommend the next step** (§5.3.1 #6):

```
Stage 4A complete — Automation Package → Pending Automation Approval
```

# 36. Observability — what this stage emits

**This stage emits facts. It does not compute metrics.** Durations, counts and ratios are derived by
`platform_core/tools/observability` from the events below; no formula belongs in this specification
(`pipeline.md` §15).

Every event this stage records carries `--source skill`, which is a claim about reliability, not a
label: a Skill event is emitted because this document says to, so its presence is trustworthy and
**its absence proves nothing**. Platform tools emit their own `platform-tool` events from code, and
the two are never counted as one class. Recording honestly matters more than recording flatteringly —
a missing `STAGE_COMPLETED` makes the run `Partially Instrumented`, which is the correct outcome.

```bash
node platform_core/tools/observability/cli.js record --source skill --type <TYPE> [flags]
```

## Always

| When | Event |
|---|---|
| This stage starts | `STAGE_STARTED --stage 4A` → keep the returned `spanId` |
| This skill starts | `SKILL_STARTED --stage 4A --skill automation-skill` |
| This skill finishes | `SKILL_COMPLETED --span-id <id>` |
| This stage finishes | `STAGE_COMPLETED --stage 4A --span-id <id>` |
| A Human Decision is raised (`pipeline.md` §5.5) | `HUMAN_DECISION_REQUESTED --decision-id <id> --category <Requirement\|Architecture\|Safety\|Review\|Automation\|Execution\|Other>` |
| That decision is answered | `HUMAN_DECISION_RESOLVED --decision-id <id> --status <answer>` |
| An artifact is first written | `ARTIFACT_CREATED --artifact <path> --artifact-class <class>` |
| An existing artifact is revised | `ARTIFACT_UPDATED --artifact <path> --artifact-class <class>` |

**Close every span you open.** An unclosed span is reported `Incomplete` and receives no duration —
never an elapsed-time estimate. **Declare the decision category explicitly**; it is never inferred
from the text of the question.

## Specific to this stage

| When | Event |
|---|---|
| Cases are selected for automation | `AUTOMATION_GENERATED --status Selected --count <n>` |
| Tests are newly written | `AUTOMATION_GENERATED --status Generated --count <n>` |
| Existing tests are reused unchanged | `AUTOMATION_GENERATED --status Reused --count <n>` |
| Existing tests are modified | `AUTOMATION_GENERATED --status Modified --count <n>` |
| A compile or build finishes | `AUTOMATION_BUILD_RESULT --status <Passed\|Failed>` |
| A self-review iteration revises the suite | `ARTIFACT_UPDATED --artifact-class automation` |

Keep the four `AUTOMATION_GENERATED` statuses distinct. Collapsing *Generated* and *Reused* into one
"produced" number would let a run that reused everything report the same output as one that wrote
everything, and §26 exists to prevent precisely that.

**Emitting telemetry changes nothing about eligibility.** The gate is still
`Review = Approved AND Automation = Approved`, unchanged, and §27A's rule that generation permission
is not execution permission is unaffected.

## Never emitted by this stage

- **Token counts or cost.** No event type exists for them. No supported run-attributable provider
  usage source exists, and nothing is estimated from text length or hardcoded pricing (HD-OBS-002).
- **A metric, ratio, or score.** This stage records what happened; the aggregator does the arithmetic.
- **A secret.** No password, token, API key, session ID, cookie, authorization header, or card detail
  reaches `--metadata`. Credential *identities* and roles are acceptable where genuinely needed.
- **A coverage percentage.** Coverage belongs to the Automation Coverage Report; the aggregator publishes only the registered formulas.

# 37. Resolving `{{MODULE_SLUG}}` and `{{RUN_FOLDER}}`

## The module: `{{MODULE_SLUG}}`

Every path containing `{{MODULE_SLUG}}` resolves to a module in the **module registry**,
`platform_core_data/modules/modules.json`, which is also the pointer recording which module(s) the
pipeline is currently working on (`workflows_and_pipelines/pipeline/module_architecture.md` §6).

```bash
node platform_core/tools/module_manager/cli.js active --json   # -> the slug(s), and the scope
node platform_core/tools/module_manager/cli.js list            # every module, status, active marked *
node platform_core/tools/module_manager/cli.js show <slug>     # one module's full state
```

- **Never hand-format, guess, or infer a module slug.** Resolve it from the pointer. A slug written by
  hand is a folder that may not exist, and a stage writing into it creates a module nothing can find.

**Feature scope — resolving `{{FEATURE_SLUG}}`.** A module may hold standalone **Features** at
`modules/{module}/features/{feature}/`, each with its own independent stage tracking
([`module_architecture.md`](../../../workflows_and_pipelines/pipeline/module_architecture.md) §5.5,
[`new_us_intake.md`](../../../workflows_and_pipelines/pipeline/new_us_intake.md)). Resolve the pair,
never one half of it:

```bash
node platform_core/tools/module_manager/cli.js active --json     # -> activeModules[] + activeFeature
node platform_core/tools/module_manager/cli.js feature list [<module>]
```

| `activeFeature` | Scope | This stage resolves |
|---|---|---|
| `null` | consolidated module / CRUD | `{{MODULE_SLUG}}` only — and confirms the Feature pointer really is null |
| set | that standalone Feature | **both** `{{MODULE_SLUG}}` and `{{FEATURE_SLUG}}`; artifacts go under `modules/{module}/features/{feature}/` |

- **An invalid or stale Feature pointer is an error, not a fallback.** A Feature naming a module it
  does not belong to, or one that no longer exists, means the tooling no longer knows what scope the
  human intended. **Stop and ask for correction** — never quietly continue at module scope, which
  would write Feature output into its parent's folders.
- **Feature artifacts stay inside the Feature boundary; module CRUD artifacts stay inside the parent
  module.** Neither writes into the other.
- **A Feature stage never advances the parent module's stage**, and the reverse holds too. Record
  Feature progress with `cli.js feature stage <module> <feature> <stage>`, module progress with
  `cli.js stage <module> <stage>`.
- **A module with no `features/` folder is normal**, not incomplete: it is CRUD-only scope.
- **No active module → ask, never assume.** Stop and ask which module to work in, listing what exists.
  Never fall back to "the only module," "the newest," or the first alphabetically.
- **A pointer naming a module folder that does not exist → report it and stop.** A stale pointer means
  the module was never scaffolded or was removed; writing elsewhere would corrupt both records.
- **Never create a module.** Only Stage 1 may *propose* one, and only a human may approve it
  (`module_architecture.md` §6.4). A missing module is a question, never a thing to fix by creating it.
- **The pointer is sticky, and switching it is the human's call.** It stays on the same module(s)
  across invocations. This stage never rewrites it to redirect its own output.
- **Multi-module scope means once per module, never one merged artifact.** When `activeScope` is
  `multi` or `full-project`, produce this stage's output separately under each module in scope. The one
  exception is an *execution* result, which is per run by definition (`pipeline.md` §7).
- **Record progress through the Module Manager, never by hand-editing `modules.json`.** It is the only
  sanctioned writer of the registry (`module_architecture.md` §6.5 Rule 3).

This stage **writes into the module**: `modules/{{MODULE_SLUG}}/automation/`, a standalone project. Its one write outside the module is `automation_baseline/{framework}/shared/`, for genuinely shared assets (`pipeline.md` §12.1).

**Staleness is reported, never silently resolved.** When an upstream module artifact has been revised
since this stage last consumed it, say so — in this stage's own output and in the closing message. Re-
running an upstream stage is a human decision at that stage's gate (`module_architecture.md` §10.4).

## The run: `{{RUN_FOLDER}}`

Every path in this specification containing `{{RUN_FOLDER}}` resolves to the **active run**, recorded
at `platform_core_data/runs/current_active_run.json` — the single fact that says which of a project's
many runs the pipeline is currently working in (`workflows_and_pipelines/pipeline/run_manager.md` §5.7).

```bash
node platform_core/tools/run_manager/cli.js active   # -> the run folder name to write into
node platform_core/tools/run_manager/cli.js list     # every run, newest first, active marked *
```

- **Never hand-pick, guess, or infer a run folder.** Resolve it from the pointer (`resolveActiveRunFolder()` in JS, or the `active` verb). A stage that writes into a run it guessed at is exactly how one logical run's artifacts end up scattered across several folders.
- **No active run → ask, never assume.** If the pointer is absent, stop and ask which run to use, listing what exists. Never fall back to "the newest run" or create one silently.
- **A pointer naming a missing folder → report it and stop.** A stale pointer means the run was deleted or renamed; redirecting this stage's output into some other run would corrupt both.
- **The pointer is sticky.** It stays on the same run across invocations until someone switches it, so a multi-stage session keeps writing into one run without restating which.
- **Switching runs is the human's call.** This stage never rewrites the pointer to redirect its own output. Working on a different run means the switch happens first, as an explicit step (`cli.js use <run>`).

This stage never creates a run. Its working copy (`modules/{{MODULE_SLUG}}/automation/tests_{Framework}/`) and every report it writes belong to the active run. The Workspace Automation Baseline (`automation_baseline/{framework}/`) and the Automation Package Registry are deliberately **not** run-scoped, and are unaffected by which run is active.

## Inherited artifacts and code drift

A run may be a **refinement** of an earlier one (`run_manager.md` §5.9). Such a run carries
`metadata/lineage.json` recording `inheritsFrom` / `supersedes`, and its inherited artifacts live in
the prior run and are **referenced by path, never copied** (`pipeline.md` §7 "Cross-run reuse").

```bash
node platform_core/tools/run_manager/cli.js drift          # what moved in the app since this run was anchored
node platform_core/tools/run_manager/cli.js drift --json    # machine-readable, exit 2 when not "unchanged"
```

- **Resolve `{{PRIOR_RUN_FOLDER}}` from the lineage record**, via `resolvePriorRunFolder()` — never by
  picking a plausible-looking earlier run. A run with no lineage record inherits nothing.
- **An inherited artifact is an input, not a conclusion this run has re-established.** Cite it by its
  prior-run path so a reader can see it was inherited rather than produced here.
- **Drift decides what may be reused as-is.** When `drift` reports `moved`, every inherited finding,
  test case, or locator touching a changed path is **unverified against current code** until this run
  re-checks it. Say so explicitly rather than presenting it as still current.
- **`unknown-*` is not `unchanged`.** No anchor, no git, or an unresolvable ref all mean drift could
  not be computed — treat inherited conclusions as unverified, never as confirmed.
- **A refinement targets today's project state.** The prior run described the app at its own
  `targetRef`; this run describes it now. Never carry forward a conclusion that drift contradicts.

# Controlled mutations (Phase 9.4)

Every write this stage makes outside the run folder and the module working copy goes through a command that checks it first. A direct file write to these places is outside the supported workflow.

| Write | Command | Refused when |
|---|---|---|
| Target or Reference Project (§11C Target Write Plan and Ledger) | `target_write/cli.js plan --run <run> --root TP-n --changes <changes.json> --environment <env>` → a named human `approve --plan TWP-n --approved-by "<name>"` → `apply --plan TWP-n` (`register-root` once per project, by a named human) | unregistered root; a path that is absolute, has `..`, is in `.git`, escapes through a link, or is outside the run's `--scope-paths`; another module's or a shared file; an unowned existing file; Execution Safety not Allowed; no approval, or an approval for a different fingerprint; the target or the content changed since approval. Every attempt is in `metadata/TargetWriteLedger.md`; a failure part-way is rolled back, an interrupted one is restored by `recover` — unless someone else changed a file since, then recovery stops (`RECOVERY_CONFLICT`), keeps their version as evidence, and a named human chooses `--resolution keep-current | restore-approved`. Roots are registered at a git work tree's top only; drive roots, system, home, broad personal and temp folders are refused (Phase 9.5) |
| Promoted module, in the baseline | `automation_lifecycle/cli.js plan-baseline-update --module <m> --baseline <dir> --reason "…"` → `record-baseline-update --update BU-n --approved-by "<name>"` | a changed path the module does not own (another module's, unowned, the ownership manifest); a shared path without an approved shared change; the module moved past the plan's restore point; the disk differs from the planned commit |
| Shared asset (`shared` patterns) | `plan-shared-change --path <p> --operation create|replace|delete [--source <file>] --reason "…"` (impact analysis) → `approve-shared-change --change SAC-n --approved-by "<name>"` → `apply-shared-change`, or a merge / baseline update carrying exactly that content | the path is not declared shared; no approval; the content or the baseline file changed. A module merge never replaces a shared file on its own |
| Module working copy (seed) | `automation_lifecycle/cli.js copy-in --module <m> --baseline <dir> --package <modules/m/automation/tests_X>` | not that module's folder; a Promoted module; a folder that already holds files |

- **Live browser sessions need the stage's Safety Preflight** — record `run_manager/cli.js state preflight 4A --environment <env> --target-url <url> --execution-type browser --execution-mode Headed|Headless --operations <ops.json> --confirmed-by "<name>"` first, then pass `headless` (the human's answer) and `preflight: { runsDir, run, stage: '4A', id: 'SP-n' }` to `BrowserDriver.authenticate()` / the Browser Provider. # Run State Integration (pipeline.md §5.3.2 — added 2026-10-08)

This stage (`4A`) records its lifecycle in the run state model. These commands are mechanical. They never replace a reviewer's decision and never skip a gate. The full rule, and every stage's row, is `pipeline.md` §5.3.2.

1. **Entry — before any work:** `node platform_core/tools/run_manager/cli.js state start 4A --invocation <Pipeline|Direct|Direct (degraded)> [--instruction "..."]`. This runs the entry gate. **Exit code 2 means blocked:** do not start. Show the human the reasons, request what is missing (`pipeline.md` §5.3.1 #4), and name the next command. Without an approved Manual Test Suite the gate blocks, unless the invocation names the test case IDs: then `--invocation "Direct (degraded)" --named-test-cases`.
2. **Artifacts:** `node platform_core/tools/run_manager/cli.js state artifact 4A --artifacts <path[,path]> [--kind checkpoint|output|evidence]` for what this stage writes.
3. **Exit — this stage has a checkpoint:** `node platform_core/tools/run_manager/cli.js state request-approval 4A --artifacts <checkpoint artifact>`. Its checkpoint artifact is `platform_core_data/modules/{{MODULE_SLUG}}/automation/AutomationPlan_{Framework}.md`. Finishing the work never marks the stage Completed.
4. **Approval:** only after the named reviewer approves and the artifact's own Status header reads `Approved`: `node platform_core/tools/run_manager/cli.js state approve 4A --approved-by "<reviewer>"`. It is refused if the header says anything else, or if the artifact is missing. A rejection: `state reject 4A --rejected-by "<reviewer>" --feedback "..."`.
5. **Blocked or failed:** `state block 4A --reason "..."` or `state fail 4A --reason "..."`, so the run records what it is waiting on.
